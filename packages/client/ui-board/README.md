# @deepseek-ai/dsh-client-ui-board

English | [中文](README.zh.md)

## Summary

The board is a spatial main panel for the dsh web client: an infinite canvas of movable, resizable, stackable agent windows, each owning a Harness session and the chat composer. The lane renders every tool call as a card with elapsed seconds, localized failures, and a JSON fallback, and banners a pending approval before navigating to the main panel's answering composer. A bottom dock lists windows and opens the window catalog, a top-right minimap mirrors the layout, and each window carries a working-folder panel and a tabbed file panel. It draws the `board` panel on the shared theme.

## Use this package

Open the board panel through the switch beside the sidebar brand; the board's mode badge sits at the same screen position and returns to the standard interface, so switching moves no control (Т2.5/Т2.6). The board's main panel declares itself sidebar-less, so the shell's sidebar column, its rail, and its resize handle stand down while the board is selected; the canvas fills the main panel and starts empty. Drag the background to pan, wheel or two-finger swipe to pan, and `Ctrl/Cmd+wheel` (a trackpad pinch) to zoom proportionally around the pointer (0.2–2.0); the dock's plus button opens the window catalog (an agent window, the preset submenu, connectors, settings, a clone, the dashboard's unavailable notice, tasks, and the recent chats), and the element-picker button beside it arms the inspector for the active chat window. Window interactions follow one convention: drag the header to move, drag an edge handle to resize one axis, drag a corner handle to resize both axes independently, and hold Shift while dragging a corner to scale proportionally (both axes by the same factor, the opposite corner anchored) or Alt to release the 24 px grid snap; clicking a window brings it to the front of the z-order, and its close button removes it. A Space-drag or a middle-button drag pans from anywhere on the board — the floating chrome included, and a middle-button drag on a handle pans instead of resizing — and `Ctrl/Cmd+0` resets pan and zoom while the pointer or focus is on the board, `Ctrl/Cmd+=`/`−` step the zoom around the board centre. A wheel over a window lane, an open window panel, an open menu, or the dock scrolls that surface (the dock sideways, a vertical wheel included) while a wheel over the canvas or the rest of the floating chrome pans; `Ctrl/Cmd+wheel` zooms anywhere over the board, windows and panels included. The active window's eight resize handles are also drawn above the floating chrome, so an edge that slid under the dock or minimap stays grabbable. The ring sits just outside the frame, so the header's controls stay clickable even when a zoomed-out canvas scales them below the strip's thickness. A window that leaves the visible canvas stops painting — its lane, draft, attachments, and panels stay live — and returns unchanged when the view comes back. Escape performs one action per press in the order menu, focused editor, element selection, open window panels. A window never shrinks below the minimum working layout (408×480 for a chat window) — the header, composer, and lane cannot lay out in less — while growing in width, height, or diagonally is unbounded. Below `detailZoomThreshold` (default 0.4) the window swaps its detail chrome for a simplified card carrying its name and session status — the lane, composer, and header stay mounted but hidden — and a click on the card raises the zoom back to the threshold and centres the window; the frame handles, the screen-space handle ring, and the window’s own open menus stand down with the detail view, and the dot grid doubles its step and fades its dots while the screen-space step is under 8 px. New windows open centred in the board's safe area — the viewport less the floating chrome's measured insets — and centring a window lands it on the safe area's centre, so neither lands under the dock, the mode badge, or the minimap. The window renders one scale above the app: its titles, lane text, chips, controls, and composer read one metric set (`--board-font-*` and the control, padding, and gap values) declared on the board root, so the frame and its contents grow together while the dock, minimap, and portalled menus keep the app's sizes. The window's own header carries the two panel controls — the left one opens the working-folder panel, the right one the file panel — and each panel slides out of its edge: the window's control surface for projects and chats, and its file tabs. Both panels belong to their window: each opens independently and keeps its own width in the layout (the left 260–360, the right 280–600), they ride the window's own stacking level so the frame paints above their inner edge, and both use the same slide-out motion, which `prefers-reduced-motion` drops. Opening a panel that would fall outside the visible board shifts the canvas to make room without changing the zoom, and the culling margin covers an open panel so a window is never hidden while its panel is visible. The panel is a working-folder tree: every registered workspace is a row in registry order — a folder with no chat yet included, because that folder's first chat is created from its own group — plus an ungrouped bucket, and the panel header registers a folder (the browser lists one directory level with clickable crumbs and creates nested folders before registering the picked directory; a host that mounted the native chooser instead serves no listing, so the panel then hands the pick to that chooser and registers what it returns), opens a search field, and opens the grouping and ordering menu (group by project or one list; manual order or last updated). Expanding a folder lists its chats in place with their relative age and a running marker, and picking one points the window at it — or, when another window already shows that chat, brings that window forward and leaves this one alone — while the panel stays open. Every row has a trailing menu — projects rename, move up or down, copy the path, open the folder, and delete (a registration only; chats and files stay), chats rename, branch at their last completed turn (the window then shows the child), move, and archive — each folder row carries its own New session control, and a drag on a row commits the same move. The tree keeps one density step below the sidebar: 28px session rows, 30px folder rows, a 32px header, and 13px labels. The window session's own folder opens automatically, and the expanded set lives in the board store, so the tree returns as it was left when the board remounts. The right panel carries the session's file surface: a tab strip with `+` and the collapse control, a Home tab offering Workspace files, a Files tab listing the session workspace root with its path and Reload, and a viewer tab per opened file (images, PDFs, Markdown, text; the document-preview registry picks the loading mode). Tabs belong to the session and a repeated path activates its tab instead of duplicating it, and file links in the lane — artifact chips, tool-card file chips, and path-like inline code — open a viewer tab and reveal the panel. Each panel is a layer of its own above the canvas at the frame's own height, following the window while it moves, resizes, pans, or zooms; its outer edge resizes it within the side's range. A closed panel takes no width, and the window's header control reopens it; the panel's own header collapses it again. The minimap stands down while any window panel is open — a panel is a management surface — while the bottom dock stays visible through it (Т1.14); closing the panels brings it back. Escape closes the window's open panels. Selecting a window in the dock or minimap focuses it and centers the view on it, except that the active window's dock row only raises it while the view is on that window — a view that moved off the active window is brought back, so the row is never a dead gesture. Every dock row shows the window's icon — a chat window's first title letters on a circle tinted deterministically by its working folder (neutral without one), a clone's initials, or the kind's glyph for settings, connectors, dashboard, and tasks — and dragging an icon past a 5px threshold reorders it inside its own group (windows among windows, clones among clones, an insertion bar in the gap), scrolling the strip near an edge and swallowing the click the finished drag leaves behind; the order lives in the layout, and resolves the window's title, its kind, and the status its session channel reports — Creating or Restoring while the session is absent, pending, or waiting for the session list, Running while a turn runs, Error on a creation, prompt, turn, or vanished-session failure, and Idle otherwise — and the row's localized accessible name pairs the title with that status; a right-click opens the row's portalled menu with Rename (an in-place editor) and Close window, which removes the window while its chat stays alive and listed. Past the second divider the dock's clone strip lists the deployment's clones, one compact icon each, and clicking one opens that clone's editor window — or brings it forward when it is already open; the header and the dock name the window with its chat's title, fall back to the kind's localized template until a chat has a title, and follow a chat rename or a rebind; clicking the header name — or double-clicking the dock row — edits a window name of the user's own, which overrides the chat title until it is cleared. The first time a window renders it creates its own session (the session appears in the sidebar list, and binding the window — on creation, on re-pointing, or on restore — opens the session's live stream without changing the shell's current session (the shell's selection moves only through explicit transitions); focusing a window only raises it in the z-order); a window restored from the saved layout reattaches to the chat it was showing, and a chat the host no longer lists leaves the window in its missing state — the lane names it and offers New session and Choose a chat until the chat returns or another is picked. The dock's `+` catalog carries a New window section — agent and tasks open working board windows, connectors and settings open windows whose bodies carry the localized unavailable-in-this-MVP line, New clone creates a clone record and opens its editor window, while the dashboard answers with its localized unavailable-in-this-MVP notice — plus a recent-chats section listing the six most recently updated chats with their directories (reopening one follows the same bring-forward rule); every board menu is portalled and opens on the roomier side. Clicking an element while the inspector is active captures a deterministic `tag:nth-of-type(n)` selector path — anchored at the board surface, or at `body` — plus a language-neutral description of the element's tag, containing window kind and title, `data-board-action`, accessible name, tooltip, and a 60-character text excerpt, and appends the localized chip to the addressed window's composer draft under the same active-chat-window-else-new-agent-window rule; the overlay passes pointers through, claims the click in the capture phase so the control under it never activates, yields to an open menu, and Escape cancels. The composer mirrors the main chat: `+` opens the action menu (files and images, goal, plan, feedback, compact, permission, export), `/` filters the slash commands with their hints and descriptions, `@` suggests files, directories, and sessions with a localized kind, the chip row switches the permission preset (full access behind the risk confirmation) and the model with its reasoning effort, and the ring shows context occupancy — the empty mark before the first provider report, then the normal, warning (above 80%), and critical (above 95%) states tinting the arc and the reading, with a `% · used / window` tooltip in compact units — and the microphone button dictates into the draft through the browser's speech recognition where the engine exposes it; a line that leads with a known command executes against the session with its arguments — and with the draft's images and staged files, so a command that does not accept attachments is refused by the host with its own reason — while images obey the host's projected limits (a batch over the count, per-image size, or total is refused with the localized reason) and other files upload in the background and ship as receipts; the card also accepts files dropped onto it or pasted into the field; the agent-preset chip is the only setup chip in the composer (the working folder lives in the window's chats panel), and the panel's folder action registers a picked directory as a project folder for new chats; a new window starts with the board's remembered preset — the last preset picked in the chip or through the dock catalog's Preset entry becomes the default, is stored with the layout, and is applied to the window's fresh blank session — while a preset the host refuses renders its localized reason under the composer, a session that already started disables the chip with that reason in its hint, and a preset that cannot compose a session is never offered; the model chip's tooltip names the model and the reasoning effort in force and states that a switch is saved as the system default for new sessions, and a model-catalog failure renders inside the model menu while the window keeps working. Enter sends, Cmd/Ctrl+Enter steers the running turn, Shift+Enter inserts a newline, and the round button stops; every send registers a local echo in the lane before the host admission, and the draft and its chips return untouched exactly once when the host refuses the prompt (a composer the user has typed into keeps its newer text and gains the refused draft as a new paragraph); a queued message renders in the strip above the card with its attachments and offers edit (its text only), remove, and steer while a turn runs, queued echoes still awaiting their occurrence render as sending rows, a refused queue change shows the host's reason in the strip, and a cancel keeps the queued work the host resumes in order; steering corrections — pending and durable — render in the lane as their own user bubbles, and a durable turn failure renders as one localized card whose expandable detail carries the provider message and code and whose repeat action re-sends the failed turn's prompt, with the channel's generic failure line appearing only when no card carries that failure; the card measures itself so the tool row never wraps — the permission and model chip labels keep their first word and elide the rest, then drop to their icons at the narrowest card — and the send control stays reachable at every size; `Load earlier turns` pulls the previous turns into the lane with one compensating scroll write (native scroll anchoring is disabled so the adjustment cannot double), keeping the reader's position and disabling itself while a page is in flight; the lane renders every tool call as its card and keeps a running call's elapsed seconds visible while it executes, a call the card table cannot read falls back to a collapsed JSON block, a settled result whose call is outside the loaded window keeps its unavailable line with a repeat control, and the empty, creating, failure, running, and blocked states each render their own localized line; and the chat window's header carries the expand-to-standard button (Т2.1): it hands the window's unsent draft to the session's own composer, selects the session, and returns to the standard interface. The tasks window lists the deployment's autonomous clone tasks newest first, one row per task with its status pill, objective, and relative age; a pending task offers Start (which creates the session the task then runs on), every pending or running task offers Cancel, a task with a session opens it in a chat window, and a running task shows its admitted goal rounds against the task's cap. A window opened from a clone's Autopilot form starts scoped to that clone — the filter row switches between this clone and all tasks — and carries an Objective form that stores and starts a task without leaving the window; the row's Report toggle expands the task's Markdown summary and the file artifacts folded from its session transcript. While any task in the window's visible scope is pending or running the body re-reads that roster every 750ms and stops with the last active visible task.

The client plugin's `Config` carries the wheel behavior: `wheelMode` is `'pan'` (default: an unmodified wheel over the canvas or the floating chrome pans) or `'zoom'` (it zooms the canvas instead), and `zoomSensitivity` is the `k` of `factor = exp(−Δ·k)` (default 0.0023, so the ≈300px of a full two-finger pinch changes the scale about twofold); `detailZoomThreshold` is the zoom below which a window shows its simplified card (default 0.4, the R-6 decision).

A clone window edits one clone record and, while its profile is being drafted, hosts the interview that drafts it. The window state carries the record's `cloneId` (persisted with the layout, so a restored clone window reopens on its clone), and a three-tab strip sits between the header and the body: Profile renders the card form — name, role, summary, persona, methodology, preferred model route, and lifecycle status (`draft`, `interviewing`, `ready`) — beside a revision indicator and the record's updated time. The methodology field reads the live draft against the four canonical sections: the stored headings stay the canonical markers, while the chips and the gap hint render in the interface language and each unfilled chip keeps its localized `empty`/`missing` mark; it names the gaps in a hint and offers `Insert template` while the field is blank. A Skills section lists one row per skill — its name and its description, or the warning for a non-kebab name, a duplicate, or a description still empty — and its trailing menu offers edit and delete, following the chats panel's row-menu convention; its add button opens a modal that enforces the kebab-case name, uniqueness, the 100-skill cap, and the length bounds. Interview renders the window's own Harness session in the same conversation body every chat window uses, so the interview is an ordinary chat with the ordinary composer, and Memory switches the window's body to `clone-memory` and renders the clone's stored memory from `/api/ketos.memory`: status filter pills for `active`, `candidate`, and `archived`, a search field whose query matches tokens as quoted prefixes with a clear control, one row per memory with its status, source session (or `the person` when none), update time, content, and tags, an inline editor for the content, tags, and status, and a delete behind one confirmation, but no create control — a new memory is written by the agent through `clone_memory_remember`, and the window verifies, edits, and deletes what it saved; a read the route refuses renders its own failure row with a retry instead of an empty memory, every accepted change re-reads the list, and the host rebuilds the clone agent's memory snapshot so its next turn sees what the person left. `Start interview` (or `Restart interview` once a profile exists and the old draft is kept until the new save replaces it) marks the clone `interviewing` under the revision the form read — a refusal there is the whole failure, so nothing half-started is left behind — then creates a session, binds it with the interview role, and hands that session to this window, which switches to the Interview tab; the host composes the interview instruction and the draft-save tool into that one session and opens the conversation with a kickoff turn, and the strip shows the brief instruction and the number of answered exchanges while the status is `interviewing`. Saving the card through `/api/ketos.clones` stays revision-checked: a card changed elsewhere answers `changed elsewhere` and re-reads the record, so saving again overwrites the newer revision, while a clone that left the roster leaves the window in its missing state. The board re-reads the clone roster whenever an interview turn settles, so a profile the agent saved appears in the form; fields the stored record moved are marked `Updated by the agent`, the user's unpublished text always survives, and a dirty draft holds the stored revision as a pending row that one click applies. A clone that turns `ready` under a live interview raises a review notice that opens the Profile tab. The form's unsaved text survives the agent's revision: the stored values wait in a pending row until the user applies them, and the user's own save is never shown as an agent revision. Delete asks for one confirmation, then removes the record, its session bindings, and its editor windows; the bound-sessions list below the form opens any binding — the window's own interview switches this window to its Interview tab instead. The preferred-model picker offers the deployment's model catalog and `Deployment default`, stores the pick as a `provider/model` route, and a new interview session starts on it; the pick applies to that clone's sessions alone, so the `agent-default-model` system default new ordinary chats follow stays where the user left it. The frame and the dock name the window after the clone — the interview session's generated title never renames the record's window — until the user renames it. The form's unsaved text and the agent-change marks are kept across the tabs: they live in the board store, so switching bodies never drops them.

## Understand the implementation

**Runtime invariant:** No companion is published. The panel entry registers the `main` slot with the single engine store and declares the layers it renders; the entry's disposal proves removal, independently observable through the `board.*` slot declarations.

<details>
<summary>Implementation internals — click to expand</summary>

One registration surface: `apply` composes the board as slots. The `main` panel entry declares `board.canvas`, `board.dock`, and `board.minimap` and renders them through `renderSlot`; the canvas occupant declares `board.windows`; the window layer declares the keyed `board.window` (one registration per window type — the instance travels in owner props, so one occupant serves every window of its type) and the keyed `board.window.body` (one registration per body kind — the connectors, settings, and dashboard kinds share the unavailable-notice occupant), and the keyed `board.window.panel` (the chats panel, registered for the agent and clone windows), and hands each frame the body dispatcher; the same `apply` registers the interface switch in the sidebar brand row (`sidebar.brand.actions`) and the return control in the Session header's utility row (`conversation.session.header.utilities`), and the board's mode badge renders in the board root; an effect on the Session list moves the expanded window onto a Session the user opens in the standard interface (Т2.13–Т2.16). The keyed keys are the `WindowKind` and `WindowBodyKind` unions, so a registration for an unknown key is a compile error. Board state is one `dsh-client-store` engine store declared at the panel entry — pan, zoom, viewport box, window map, z-order, and the element-selection flag — with pure draft actions (`setPan`, `panBy`, `setZoom`, `zoomBy`, `resetView`, `setViewport`, `addWindow`, `openWindow`, `moveWindow`, `resizeWindow`, `setWindowBodyKind`, `focusWindow`, `centerOnWindow`, `closeWindow`, `hydrate`, `setSelectingElement`, `setExpandedWindow`, `reorderDock`, `reorderClones`) plus the per-window composer drafts (`setDraftText`, `appendDraftText`, `addDraftImages`, `addDraftFiles`, `updateDraftFile`, `removeDraftItem`, `clearDraft`). Durable layout is the Host settings namespace `ui-board`: `board-settings.ts` owns the versioned schema, `client/board-layout.ts` captures the store into the wire document and repairs a stored one, and `client/board-persistence.ts` adopts the first-frame cache and, through the shared settings describe mirror, the server document, and writes changes back debounced under the revision CAS. The window z-index band is capped below the floating chrome, and raising a window writes only that window's value, so the other windows keep their state identity. Every layer and frame reads that same handle through the framework `useStore` seat; components hold no subscriptions of their own — the header drag and each resize handle are leaves that read the zoom where their gesture starts, so a canvas zoom never re-renders a window body, and the chats panel subscribes to the view transform only while it is open. Visible copy is locale-owned: `apply` registers the `board` namespace dictionaries through `ctx.locale` and each copy-bearing entry declares the namespace, which puts the typed `t` seat on its component. Styling reads the shared theme directly: each component owns a CSS Module beside it, inline styles carry only placement and the computed pan/zoom metrics, and the rules name `--dsw-*` semantic aliases — floating panels use the theme's layer-2 fill with an elevation hairline (rebound to the business accent on the focused window), internal separators are 0.5px hairlines, and the canvas dot grid rides the border scale. Interactive chrome comes from `ui-primitives`: header close buttons and the composer actions are Harness icons, the dock rows and the composer action are wrapped in `Tooltip`, the dock's window catalog is the shared `Menu`, and the dock controls sit on the floating-fill token. Board popovers share one screen-space layer in the board root — above the dock and minimap, below the element-selection overlay — and every window frame, chats panel, and dock hosts its tooltips and menus through it: window popovers render at the board zoom clamped to the board box, the screen-space chrome renders at 1, and a window menu follows its trigger through pan and zoom but closes when its window moves, resizes, culls, or closes. The board therefore follows the shell's light/dark preference like any other panel. Gestures have one owner: every drag (canvas pan, header, window resize, panel resize, row reorder, dock icon reorder) goes through `pointer-gesture.ts`, which ends on pointerup, pointercancel, or the owning component's unmount, so no listener or capture survives a gesture. The board root owns the non-passive wheel and Safari gesture listeners: ctrl/meta zooms anywhere over the board, a plain wheel pans — or keeps a window lane, an open chats panel, or a menu scrolling — and ctrl+wheel anywhere zooms while the page pinch stays blocked; a `ResizeObserver` on the canvas container is the single owner of the measured viewport, and windows that leave the canvas hide with `content-visibility` — never unmounted — through `culling.ts`. Window sessions live in an apply-side bridge (`session-bridge.ts`): the window id → session map, the `sessions.create()`/`openStream()`/`binding()` sequence, and the chat/session subscriptions all stay in the plugin closure, never in the store, and each window's lane state — the assembled chat, the chat title, the history flags, the running calls, the image limits, and the turn and prompt failures — is republished through one identity-stable channel per window; closing a window drops its bridge record, while the session itself stays alive and listed. The map is durable: the bridge hands it to the persistence layer on discrete events (creation, rebind, close) and the settings section carries it as `bindings`, written as a complete-section replace so a closed window's pair actually leaves the section, and every adoption restores each window's chat; `sessions.list` is the authority that moves a bound window between restoring, ready, and missing, reattaching a chat that returns, and one session belongs to one window — `bind` reports duplicate, same, and unknown outcomes, and the panel and the dock catalog's recent-chat list bring the holding window forward instead of opening a second one. The frame and body registrations expose that channel as the keyed hook `useWindowSession(windowId)` plus the composer callbacks (`ensureWindowSession`, `sendPrompt`, `cancelPrompt`, `loadOlderTurns`, `executeCommand`, `uploadFile`), so one registration serves every window and components receive plain data; `uploadFile` stages non-image files through the host's background upload service and hands the composer a receipt the prompt or command carries. Board chrome shares its addressing and placement rules: `open-window.ts` resolves the chat window a command acts on (`resolveChatWindow` — the active chat window, else a fresh agent window), the store's `composerIntents` queue carries append-text and open-file-picker commands until `ComposerBar` consumes them (a file picker waits until the composer can accept files, and a closed window drops its queued commands), and the store's `drafts` map holds each window's unsent composer draft in memory — the board unmounting for the standard interface keeps the text, images, and staged files, while closing the window drops them and the layout never carries them, `element-capture.ts` builds the deterministic selector and language-neutral description behind the inspector chip, and `menu-placement.ts` is the single rule every board popover uses to open on the roomier side. Below `detailZoomThreshold` each frame swaps its chrome for the simplified card through one `useStore` boolean selector, so the twenty-window board re-renders only when a window crosses the threshold; `BoardRoot` arms `will-change: transform` on the canvas surface from the pointerdown that starts a drag and from every wheel or Safari gesture event, and drops it 150 ms after the last one, so the surface keeps GPU rasterization only while a gesture is live. The canvas dot grid doubles its world step (24 → 48 → 96) whenever the screen step would fall under 8 px, and fades its dots toward that floor. Every floating chrome element declares the board edge it is anchored to (`data-board-chrome`) and publishes its own depth from that edge through a `ResizeObserver` on itself and the board box; the store folds the contributions into per-edge insets, `safeArea(state)` projects the free rectangle into screen and world units, and window placement and centring read it (Т1.15). A wide bottom dock therefore never takes a strip from the left and right edges.

<a id="model-experience"></a>
## Model Experience

None, as the board is a browser-only canvas: it registers no tool, prompt section, or session event, and everything it renders is board-local view state.

#### KV Cache effect

No effect; the board adds nothing to any model request and consumes no session-log content.

## Known Limitations and Deferred Work

These limits are current package constraints.

- **The window lane renders prose, steering, tool cards, and turn failures** — assistant text arrives as Markdown and streaming text is visible; each tool call renders as its card (`bash`/`pwsh`/`terminal_send` as a terminal, `read` as a file window, `write`/`edit`/`str_replace_editor` as a diff, `grep`/`glob` as search results, `web_search`/`web_fetch` as citations, `todo_write` as a to-do list, `read_image` as an image preview, `ask_user_question` as an answered transcript), and a call the table cannot read — an unknown tool, a malformed result, a call head outside the loaded window — falls back to a collapsed JSON block. A running card shows its elapsed seconds and settles into the succeeded, failed, or stopped state, with the provider's own error text under a localized failure line. Transcript nodes outside that scope — compaction checkpoints, a turn that hit the output-token cap, and model retries — render nothing yet.
- **A pending approval or question banners the window and navigates to the main panel (decided for the MVP)** — the answering UI (allow or reject, the question flow) lives in the main panel's composer, so the window shows a localized `Confirmation required` (or `Answer required`) banner whose button selects the session and returns the main area to the Conversation; the window's own composer stays inert with the banner's title as its reason until the request is resolved. The board then brings the originating window forward with a short highlight when its panel comes back. No approval surface renders inline in the window.
- **The board's file chips are draft-only** — a non-image file stages through the host's upload service and ships as a receipt while its window lives; the chip keeps the name and the retry, not the bytes or the upload progress, and a receipt cannot be re-sent after its window closes. `@` mentions insert plain text rather than editor chips.
- **Expanding a window re-uploads its staged files and reports a refused handoff** — the expand control hands the window's draft to the standard interface: the text joins the standard composer's own text as a new paragraph, and the staged files travel through the host's upload service again, so a file already uploaded for the window is uploaded a second time. A handoff the standard composer refuses — a session mid-admission, a file the composer rejects, a session the host no longer lists — leaves the window's draft in place and shows the localized reason in the window's composer until the next attempt; only a successful handoff clears the window's transferred parts. A file that came back from the standard composer is a receipt-only entry with no browser bytes: expanding again leaves it in the window, and a refused prompt marks it failed at its chip without a retry.
- **The return control brings the standard draft back into the window** — while the current Session is bound to an open board window, the Session header carries the Return-to-window button: it selects the board, centres and highlights the window, and moves the standard composer's text (as a new paragraph after the window's own text) and attachments into the window's draft — images with their bytes, files as receipts. A composer mid-admission or with an unsettled upload keeps its draft, and the window reports that the draft stayed in the standard interface. The button is the only way back: Escape never returns to the board.
- **The window composer keeps its own submission policy (decided here)** — plain Enter queues, Cmd/Ctrl+Enter steers, and the bar reads no submission-preference setting: the `ui-conversation` `busyEnter` preference lives in that plugin's settings namespace and maps only the bare-Enter gesture, while the board's windows are documented to keep the queue/steer pair on the two gestures.
- **A command's failure line may be the host's own text** — a refused handler or a rejected attachment renders after “Command failed:” in the host's words, while an unmatched line shows the board's own unknown-command line; the failure stays until the next send. The board's palette adds its own `/file` and `/model` entries (file picker and model menu) to the host registry it lists.
- **A queue edit replaces text only** — the host's edit action accepts a non-empty text-only replacement, so a queued message whose other content blocks mattered loses them; the row's image thumbnails resolve through the session-scoped conversation cache and a failed read keeps the placeholder, and the turn-error card's repeat action queues a fresh turn because the client exposes no in-place turn retry.
- **A refused queue change stays on screen until the next queue action or send** — the strip renders the host's reason under its rows; there is no per-row error state.
- **Assistant markdown keeps the app's content font size** — the shared Markdown surface reads the app's font-size setting, so only the window's own chrome, transcript text, and composer take the window scale; raise the app's font size for larger assistant prose.
- **The chats panel has no unarchive and no session delete** — archiving a chat is one-way and the client exposes no delete for sessions, so the chat row menu's delete entry is inert; deleting a project removes its registration, never its chats or files.
- **The panel's folder browser reads the browse picker only** — a host that mounted the platform-native chooser serves no directory listing, so the level names that and hands the pick to the native chooser; there is no in-app browsing on such a host.
- **The minimap stands down while any window panel is open** — a panel is a management surface, and the minimap's strip would otherwise cover a panel's outer edge and resize handle; the bottom dock stays visible through the open panels (Т1.14), and closing them brings the minimap back.
- **Resize handles follow the active window above the chrome** — the handle ring is drawn for the focused window, so a window whose edge sits under the dock or minimap still needs one click anywhere on its frame before its handles rise above those layers.
- **The dock scrolls sideways once its icons outgrow the board** — the strip grows to the board's width minus the 24px inset on each side and then scrolls sideways instead of clipping its icons and controls; a wheel over it scrolls it, a vertical wheel included.
- **Culling hides windows with a fixed world margin** — a window's contents stop painting and hit-testing once it is 480 world units beyond the visible canvas, whatever its size; its box keeps its place in the layout, the margin covers its handles and an open chats panel, and the window keeps its state while hidden.
- **Per-window setup comes from the composer** — the agent-preset chip switches the preset only while the session is still blank (the chip names that reason), the board remembers the last pick as the default for new windows, and the model chip switches the model and its reasoning effort; a model choice is also saved as the `agent-default-model` system default, which the chip's tooltip states, while a clone's preferred-model pick applies to that clone's sessions and leaves the system default unchanged. A preset never pins the model: the model is a session property, so two windows on one preset can run different models. A started session keeps its working directory, and only a still-blank session can be re-created in a newly picked folder.
- **The frame body dispatcher is an owner prop** — the windows layer is the single declarer of `board.window.body` (the slot core allows one declarer per key), so it passes each frame a `renderBody` callback instead of a `renderSlot` seat of its own.
- **The layout persists through the `ui-board` settings namespace, with MVP-scale limits** — windows, their geometry and order, the dock and clone icon orders (which are independent of the paint order, so raising a window never moves its icon), pan/zoom, the active window, each window's panel state, and the window → chat bindings live in the `ui-board` section of the user-settings document, so they survive a page reload and a process restart; a localStorage copy of the same document paints the first frame. Writes are debounced (600ms after the last gesture, at most one per second), so a crash inside that window loses the last gesture; with two tabs open, the losing writer retries once at the revision the conflict reported and the last writer wins. The expanded-window marker and the viewport box are session-only: neither is restored. A document carries `version: 1`; an unrecognized version, or a layout the schema rejects, is ignored with a warning, and the MVP has no migrations — a future version starts from a fresh board. The bindings are reconciled against the layout on every adoption — a pair for a window the layout no longer holds is dropped — and a pair whose session is gone is kept so the window can report it and reattach if the chat returns. Closing a window removes its pair too: the board writes the whole section rather than a merge patch, because the settings service deep-merges a patch and a merge could never delete the key.
- **The layout document holds at most fifty windows** — the capture writes the topmost `BOARD_LAYOUT_MAX_WINDOWS` and the schema refuses a longer list, so a board that held more windows comes back with its top fifty after a reload even though the live board itself caps nothing (the acceptance run opened a hundred windows and culled them by view; see `docs/ketos/perf-baseline.md`).
- **A live clone session follows profile and memory edits but keeps its registered skills** — a stored profile or methodology change republishes the section in place and a memory write republishes the snapshot, so the running session sees both on its next turn with no restart; the profile text is part of the request prefix, so a profile edit drops the reusable KV-cache prefix from the first changed token, while a memory write rides the next runtime-context message and leaves the prefix intact; a skills edit waits until the scope is reinstalled or the agent is recreated, because the model keeps the set its session registered at creation; [`@ketos/clone-core`](../../ketos/clone-core/README.md) owns the mechanism.
- **The completion notice needs the window to observe the transition** — «Interview complete» is raised by the clone window that sees the stored status move to `ready` while it holds the interview session; a completion that happened while no window observed it (the window was closed, or the page was reloaded afterwards) shows the ready profile without the notice.
- **The interview reports status and volume, not topic progress** — the strip shows whether the clone is `interviewing`, the instruction, and the number of answered exchanges; which checklist topics were covered lives in the conversation, and the board does not track them.
- **The interview session is reachable through its clone window's Interview tab** — picking that chat in the chats panel brings the clone window forward without switching tabs, so the tab strip (or the bound-sessions row in the form) is what opens it; the tab is disabled until the window owns a session.
- **One window per chat, and a vanished chat is not replaced** — a chat another window already shows is never bound twice: picking it brings the holding window forward instead. A chat the host no longer lists leaves its window in the missing state with New session and Choose a chat; the MVP never auto-creates a replacement, and the client exposes no session delete, so those two actions are the only recovery the lane offers.
- **Tool and settings windows ship an unavailable notice** — the connectors, settings, and dashboard window bodies render the localized unavailable-in-this-MVP line instead of real content, and the dashboard window has no creation path in the MVP; the real per-window fields arrive with the stages that own them, and a client system-prompt editor does not exist in Harness at all.
- **The dock status is a coarse four-state projection** — it reduces the window's session channel to Creating, Running, Idle, or Error with no per-tool progress; any creation, prompt, or turn failure shows Error.
- **The dock's rename and close live in the row's context menu** — no visible per-row close button exists; a right-click on the row opens the menu.
- **The inspector chip is plain draft text** — the composer has no editor chips, so the captured chip travels as text carrying a DOM description and a `:nth-of-type` selector, never a screenshot.
- **Workspace folders and project management live in the window chats panel** — working directory is immutable once a session is created (core engine constraint); new chats inherit the project's folder or run in the default working directory. The composer no longer carries a folder chip; all project creation, folder registration, path viewing, and quick actions ("Copy path", "Open folder in file manager") happen exclusively through the window chats panel.
- **The tasks roster is one shared read, a culled window keeps polling, and task artifacts come from the client's own transcript** — every tasks window filters the same roster and re-reads it every 750ms while at least one task in its visible scope is pending or running, so a task that settles while no tasks window is open shows its final status on the next open; a window the canvas culled keeps polling because the board never unmounts it, and the report's artifact list folds the session transcript this browser holds, so a task session the window never opened reports no artifacts.
- **Session artifacts are derived solely from settled tool results** — the board performs no filesystem scans and does not implement a file manager. Artifacts are gathered dynamically from successful file-access and mutation tool calls (`write`, `edit`, `str_replace_editor`, `read`) in the session's turn history, with path deduplication and mutation precedence (edits outrank passive reads). Each artifact row offers path copy and reveal in the system file manager via `session.openWorkspacePath`.
- **Isolation of user home and Ketos runtime state** — registering or setting workspace directories inside `~/.ketos` or `$DSH_HOME` is rejected both on host and client with localized validation errors; selecting a root directory (`/`, `C:\`) or the entire user home directory requires explicit confirmation.
- **The dashboard window answers with a localized unavailable-in-this-MVP notice** — its surface belongs to a later stage.
- **The context ring keeps the states and the reading, not the breakdown panel** — it carries the same occupancy value and formula as the main panel's `ContextMeter` for the window's session, and its tooltip reads `% · used / window` with compact units, but the board window has no click-open composition panel. The arc tints warning above 80% and critical above 95% of the selected model's window, and a provider that reports no usage leaves the empty mark.
- **The MVP is validated for ten simultaneously streaming windows and recommends at most 20 live chats** — every open agent window keeps its session subscribed and, while a turn runs, its stream painted (a clone window holds a session only while its interview runs, and its Profile tab holds none); the measured board held 10 windows at 60 FPS with 5 concurrent streams (`docs/ketos/perf-baseline.md`). Past 20 open chats the shared transport and the per-window session subscriptions are the cost center, so close the windows whose chats are not in use — closing a window leaves its session and list row alive.
- **Memory edits are last-writer-wins** — a memory row has no revision, so the person's edit in the memory body and the agent's `clone_memory_remember` write end at whichever lands last; the body re-reads the list after every mutation.
- **The memory window cannot create a record** — it lists, searches, edits, and deletes while a new memory arrives only from the agent's `clone_memory_remember` call, because `/api/ketos.memory` has no create operation.
