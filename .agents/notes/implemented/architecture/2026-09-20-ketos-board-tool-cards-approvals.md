# Agent Note: Board windows render tool calls as cards and navigate pending approvals to the main panel

Status: implemented

English | [中文](2026-09-20-ketos-board-tool-cards-approvals.zh.md)

## Problem

Stages 4 and 6 gave the board lane one line per tool call — the wire name plus a done, failed, or running marker — because the window could not reuse the application's tool presentation: `ui-tool`'s keyed `tool.call.toolview` slot is `scope: 'session'`, and the board renders from the root scope, where a component has no session binding for an arbitrary window (the renderer binds session-scoped slots only to the *current* session through `SessionProvider`). The feature-plugin export rule also forbids the board from runtime-importing `ui-tool`'s card models. The full `ui-primitives` blocks (`TerminalBlock`, `ReadBlock`, `DiffBlock`, `SearchBlock`, `WebBlock`, `JsonBlock`) were the sanctioned shared surface, so the lane had to derive their payloads itself.

Two more facts were missing from the window. A session that waits on an approval or a question renders its answering composer in the main panel only (`ui-approval` and `ui-user-questions` register into `conversation.composer`), so a window whose session is blocked showed nothing and the user could not tell a request was waiting. And the running-call projection on the window channel carried `{ id, name }` only, so the lane could not show a running call's arguments, its start time, or its elapsed seconds.

## Decision

**The board derives every card locally, on a deliberately narrow table.** `window/tool-card-model.ts` folds one `ToolCallBlock` — running `RunningToolCall` or settled `ToolResultNode` — into the payload exactly one `ui-primitives` block renders, with `window/ToolCard.tsx` drawing the block plus the card's status line and `window/tool-card-labels.ts` binding the board dictionary to the blocks' label props. The table maps `bash`/`pwsh`/`terminal_send` to `TerminalBlock`, `read` to `ReadBlock`, `write`/`edit`/`str_replace_editor` to `DiffBlock`, `grep`/`glob` to `SearchBlock`, `web_search`/`web_fetch` to `WebBlock`, `read_image` to a session-authorized image preview, `todo_write` to a to-do list, `ask_user_question` to an answered-question transcript, and everything else to a collapsed `JsonBlock`. This is the coverage of `ui-tool`'s shipped keyed views (`bash`, `read`, `read_image`, `edit`, `write`, `grep`, `glob`, `web_search`, `web_fetch`, `todo_write`, `ask_user_question`) plus `pwsh`/`terminal_send`, which `ui-tool` covers through its generic card, plus `str_replace_editor`, which has no keyed view at all: the board draws its intended hunk from the call's own arguments. Every reader validates its input and returns `null` instead of throwing, so a half-streamed `argsRaw`, a malformed `meta`, or a call head outside the loaded window falls through to the JSON block rather than taking the lane down.

**The running call comes from the chat snapshot, and the channel projection is gone.** The lane now reads `chat.legacy.runningCalls` — the full `RunningToolCall` with `argsRaw`, `time`, and its subcalls — so a running card shows the command or the intended diff and its elapsed seconds. `BoardRunningCall` and `BoardWindowSessionState.runningCalls` were removed: the lane was their only consumer, and the second projection could only drift from the chat it was derived from.

**A cancelled call reads as stopped, not as a failure.** The host logs `error: { name: 'AbortError', code: 'ABORTED' }` for a user cancel (observed in the live audit), and the chat assembler synthesizes `error: { name: 'Interrupted', code: 'interrupted' }` for a call left open at a turn boundary; the card treats both codes as its localized `stopped` state and only other errors as failures.

**Pending interactions reach the window through the root hook, and the action is navigation.** The window body calls `useSessionPendingInteraction` (the root source `ui-session` provides; it rides `PropsRuntime` for every scope, exactly as `ui-workspace` consumes it, so the board injects no `uiSession` service) and banners the window when its own session holds a value. The banner's button calls the new injected `openInMainPanel(windowId)`, which the apply implements as `bridge.sessionFor(windowId)` → `ctx.uiWorkspace.openSession(sessionId)` → `store.expectReturnWindow(windowId)`. While a value is pending, the window's composer is inert with the banner's title as its reason: the same state renders the banner and blocks sending, so the two cannot disagree.

**Returning to the board brings the window back.** `BoardRoot` reads `usePanelInfo` and, when the board's panel (`BOARD_PANEL_ID`) is active while `returnWindowId` is set, centers that window, clears the flag, and sets `highlightWindowId`; `WindowFrame` draws a short outline flash for it. The MCP panel id is the board's `main` registration key, so the check is one identity comparison rather than a string convention.

**Approvals keep one surface.** The window has no inline approval or question UI in the MVP: the decision itself is answered in the main panel, where the pending value already owns a composer entry, and the board only points there and marks the window to return to. The choice is recorded in the package README's Known Limitations.

## Alternatives considered

- **Render `ui-tool`'s keyed views from the lane.** Impossible as designed: the slot requires a session scope the board does not have for arbitrary windows, and runtime-importing another feature plugin's values is forbidden; a board-local derivation on the shared primitives was the only path that keeps the layering rules.
- **Extract the card models into a shared package and have both `ui-tool` and the board consume it.** Rejected for the MVP: the board's table is intentionally narrower and more tolerant than `ui-tool`'s full card surface (no persistent-shell spill handling, no `run_code` body, no attachment gallery), the extraction would drag that surface into a new package and change `ui-tool`'s ownership for one consumer, and the stage plan explicitly frames the board table as its own mapping. A second real consumer would justify the extraction.
- **Keep `BoardRunningCall` and extend it with `argsRaw`/`time`.** Rejected: the channel would mirror a chat substructure it does not own; reading the snapshot directly keeps one source and deletes a projection.
- **Block the window composer through `ctx.conversation.blocks`.** Rejected: that registry is the plugin-side way to make a session's composer inert, while the pending fact already has a root source; raising a second block from the same fact would give the block an owner the window cannot observe, and the banner's reason string is the honest placeholder.
- **Draw an inline approval panel inside the window.** Out of scope for the stage and a duplicate of the main panel's answering UI; the plan chose the navigation path, and the return highlight keeps the detour cheap.
- **Auto-focus the originating window immediately instead of on return.** Rejected: the user is looking at the main panel while answering, so the centering and flash would only be useful when the board comes back; the effect keys on the panel becoming active.

## Consequences

The lane now shows what a call did, not only that it happened: content, diffs, search groups, citations, and images render with the same blocks the main conversation uses, localized from the board dictionary, and every unreadable node has one predictable fallback. Tool windows and the restored layouts keep working — the card is a pure function of the node, and a restored session re-derives every card. The board's Known Limitations were rewritten: the one-line row and the "no indicator" limits are gone, replaced by the stopped/failed/JSON semantics and the decided absence of an inline approval surface. Because the board remains outside the per-file coverage gate (MVP fork policy), the card table is covered by behavioral specs — one node per block, running, unavailable, failed, stopped, image load and refusal, and JSON fallback — and the whole path was verified live against real host tools.

Verification: `tests/tool-card.client.spec.tsx` covers the mapping table, every reader's decline paths, and each rendered card; `tests/conversation-body.client.spec.tsx` covers the running card, the stopped transition, the pending banner with its blocked composer and navigation, and the per-kind titles; `tests/store.client.spec.ts` covers the return/highlight actions and their window-existence guards; `tests/slots.client.spec.tsx` proves the escalation path end to end in the composition bench (banner → `uiWorkspace.openSession` → return centering and highlight). The live audit (`.playwright-mcp/stage-12-tools/audit/audit.json`, `ok: true`) drove a real `pnpm ketos web` server with a scripted SSE model: bash, read, grep, write, `todo_write`, a failing read, a cancelled call, and a sandbox-escalation approval all exercised from a board window, with the same session open in the main panel showing the same calls.
