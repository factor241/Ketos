# Этап 32. Канал iroh и подключение второго Кетоса

## 1. Итог этапа

Подготовка worktree (`pnpm install`, `pnpm run build`, `pnpm run typecheck`, `pnpm exec vitest run packages/client/ui-board/tests`) — зелёная до начала правок (единственный красный прогон — известный baseline-флейк `leaks.client.spec`, кетос-r98; в этом этапе тест сделан детерминированным и проходит). Этап выполнен в worktree `/Volumes/Projects/Ketos bot.worktrees/stage-32`, ветка `stage-32-iroh-peer` от принятой `stage-31-todo-beads`; коммита нет — по правилам линии он делается после ответа «да». На VPS команды работают частные ретрансляторы iroh и Syncthing (подготовлены в 32.0); новый пакет `@ketos/peer` даёт Кетосу постоянный узел iroh с сохранённым ключом и канал сообщений «длина + тип + данные» с сервисом `ctx.ketosPeer`; «Пригласить»/«Подключить Кетос» связывают два Кетоса одноразовым кодом, известные узлы запоминаются, посторонние отвергаются; у обоих в «Участниках» два человека с именами и цветами, демо-команда удалена; связь восстанавливается без нового кода; стенд запускается по одному Кетосу на компьютер из образа, его Syncthing 2.1.5 закреплён и не ходит в публичные узлы. Доработка по итогам проверки: подписи кнопок переведены на существующий токен, опрос `ketos.peer.state` переживает сетевые сбои и останавливается только на 404, `PeerId` переименован в `KetosPeerId`, свой участник вне стенда снова получает цвет 1, дубль связи закрывается кодом `3n`, `.env.example` содержат только заглушки, живые проверки VPS и стенда выполнены заново, GIF переснят; повторная перепроверка довела заглушки в примерах до одного вида, уточнила тесты дубля и «каждого собеседника» и пересобрала каталог слотов. Ничего не пушилось и не коммитилось; `~/.ketos` не трогался.
