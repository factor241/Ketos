# Ketos: нормализованная спецификация требований

**Версия:** 1.0  
**Исследованный baseline:** `redesign/sidebar-account` @ `572fad8ea2223e342508ecf095133091c7714e1b`  
**Назначение:** единый нормативный словарь требований без технической критики. Оценка состояния и реализуемости вынесена в [02](02_KETOS_CURRENT_ARCHITECTURE_AUDIT.md), [03](03_OPENSWARM_REUSE_ASSESSMENT.md) и [04](04_KETOS_CRITICAL_ARCHITECTURE_REPORT.md).

## 1. Область продукта

Ketos должен развиваться как единая пространственная рабочая среда, в которой пользователь управляет досками, чатами, автоматизациями, заметками, результатами выполнения и проектами вручную либо через контролируемый AI-чат. Существующий backend Ketos, Flow Editor, API, KFX/LFX-совместимость и компонентная модель остаются базой продукта.

## 2. Обязательные архитектурные ограничения

| ID    | Ограничение                                                                                                                                                                           |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-01 | Во всех пользовательских и технических материалах продукт называется **Ketos**.                                                                                                       |
| AC-02 | Поддерживаются русский (`ru`) и английский (`en`) языки; системные строки не должны обходить i18n-контракт.                                                                           |
| AC-03 | Канвас, чаты, автоматизации и AI-команды используют единый backend Ketos. Параллельный backend допустим только после отдельного доказательного эксперимента и архитектурного решения. |
| AC-04 | Существующие Flow Editor, компоненты, API и KFX/LFX-контракты повторно используются; несовместимые изменения требуют версионирования и миграции.                                      |
| AC-05 | Имя класса KFX-компонента является сохранённым идентификатором и не переименовывается.                                                                                                |
| AC-06 | Внешний пространственный канвас и внутренний исполнительный граф автоматизации — разные координатные и семантические пространства.                                                    |
| AC-07 | Удаление визуального размещения объекта с доски не удаляет доменный объект без отдельной явной команды.                                                                               |
| AC-08 | AI не получает произвольного доступа к backend, файловой системе или реестру компонентов; доступны только типизированные разрешённые команды.                                         |
| AC-09 | Каждая изменяющая команда проходит аутентификацию, авторизацию, валидацию, оценку риска, аудит и обработку ошибок.                                                                    |
| AC-10 | Рискованные операции требуют preview и одноразового явного подтверждения; повтор подтверждения не должен применять команду дважды.                                                    |
| AC-11 | Миграции выполняются по схеме expand → backfill/dual-read → validate → contract и проверяются на SQLite и PostgreSQL.                                                                 |
| AC-12 | Пользовательские незакоммиченные изменения и несвязанные generated/deployment/lock/license файлы не входят в область реализации.                                                      |

## 3. Единая доменная терминология

| Русский термин          | Английский термин | Формальное значение                                                                             | Не является                                                          |
| ----------------------- | ----------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Рабочая область         | Workspace         | Граница владения, доступа и политик для пользователей/команд.                                   | Не viewport и не отдельная доска.                                    |
| Проект                  | Project           | Организационный контейнер досок, автоматизаций, чатов и документов; допускает иерархию и архив. | Не Flow и не Dashboard.                                              |
| Доска                   | Board             | Сохраняемое пространственное полотно внутри проекта.                                            | Не список метрик; термин `dashboard` в новом домене не используется. |
| Канвас доски            | Board Canvas      | UI-поверхность pan/zoom, отображающая placements и смысловые связи.                             | Не Flow Editor.                                                      |
| Viewport                | Viewport          | `{x, y, zoom}` и пользовательское состояние просмотра конкретной доски.                         | Не координаты объектов.                                              |
| Размещение              | Placement         | Визуальная проекция доменного объекта на доске: позиция, размер, слой и режим.                  | Не сам чат/Flow/заметка.                                             |
| Автоматизация           | Automation        | Продуктовое имя существующей сущности `Flow`; исполняемый граф компонентов.                     | Не окно автоматизации.                                               |
| Flow Editor             | Flow Editor       | Внутренний редактор исполнительных узлов и рёбер Automation.                                    | Не общий канвас доски.                                               |
| Чат                     | Chat Thread       | Стабильная сущность беседы с заголовком, моделью, контекстом и сообщениями.                     | Не `session_id` и не окно.                                           |
| Окно чата               | Chat Placement    | Placement чата на доске.                                                                        | Не история чата.                                                     |
| Заметка                 | Board Note        | Самостоятельный документ доски с форматированным содержимым.                                    | Не `NoteNode` внутри Flow, хотя UI может быть общим.                 |
| Результат выполнения    | Execution Result  | Сохраняемый результат конкретного запуска автоматизации.                                        | Не только transient toast/event.                                     |
| Смысловая связь         | Board Relation    | Связь между доменными объектами на доске.                                                       | Не исполнительное ребро Flow.                                        |
| Запланированный процесс | Schedule          | Правило запуска Automation по времени/событию и его состояние.                                  | Не текущий Job.                                                      |

В API и данных рекомендуется использовать `workspace`, `project`, `board`, `placement`, `automation`/`flow`, `chat`, `message`, `note`, `execution`, `result`, `relation`, `schedule`. Термины `dashboard` и `folder` считаются legacy-именами адаптеров, а не новыми доменными именами.

## 4. Функциональные требования R-01–R-40

### Пространственная среда и OpenSwarm

- **R-01.** Доска предоставляет практически неограниченное полотно, pan/zoom, сохранение координат объектов и восстановление viewport.
- **R-02.** Исходный код точного референсного OpenSwarm исследуется на уровне канваса, карточек, чатов и state management.
- **R-03.** Возможность переноса канваса OpenSwarm оценивается по лицензии, связанности, производительности, тестам и стоимости поддержки.
- **R-04.** Возможность адаптации чатового UI OpenSwarm как отдельных окон оценивается отдельно от переноса его backend и протоколов.

### Чаты

- **R-05.** На одной доске одновременно размещаются несколько независимых чатов.
- **R-06.** Окно чата перемещается, меняет размер, сворачивается, разворачивается, закрывается и переходит в полноэкранный режим.
- **R-07.** Чат хранит стабильный ID, название, историю, выбранную модель, контекстную политику и связанные placements.
- **R-08.** Закрытие/удаление placement не удаляет Chat Thread и историю; удаление чата — отдельная подтверждаемая операция.
- **R-09.** Боковая панель показывает чаты и поддерживает создание, переименование, поиск и открытие на доске.

### AI-создание и изменение автоматизаций

- **R-10.** Пользователь создаёт Automation из естественно-языкового запроса на базе зарегистрированных компонентов Ketos.
- **R-11.** При существенной неоднозначности AI задаёт до пяти релевантных уточняющих вопросов; ненужные вопросы не блокируют выполнение.
- **R-12.** Через чат можно добавлять, удалять, заменять, настраивать и соединять компоненты существующей Automation.
- **R-13.** До применения показывается структурированный diff узлов, параметров, рёбер, затрагиваемых объектов и рисков.
- **R-14.** Изменение применяется только по явному подтверждению действующего пользователя и к той ревизии, для которой построен preview.
- **R-15.** Automation имеет неизменяемые ревизии и операцию возврата/активации предыдущей версии.

### Автоматизации на доске

- **R-16.** Automation представлена на общей доске отдельным placement.
- **R-17.** Существующий Flow Editor может быть открыт внутри окна Automation при соблюдении фокусных и производительных ограничений.
- **R-18.** Полностью ручное создание и редактирование Automation сохраняется.
- **R-19.** Automation открывается в отдельном полноэкранном Flow Editor.
- **R-20.** Automation запускается с общей доски.
- **R-21.** UI различает `queued`, `running`, `waiting_confirmation`, `succeeded`, `failed`, `cancelled` и неопределённый после разрыва статус.
- **R-22.** Execution Result размещается рядом как документ, форма, карточка либо окно, не смешиваясь с данными Automation.

### Заметки и связи

- **R-23.** Заметки поддерживают перемещение, resize и форматирование; существующий опыт NoteNode используется повторно там, где совместим.
- **R-24.** Чаты, заметки, автоматизации и результаты соединяются смысловыми связями с типом и метаданными.
- **R-25.** Board Relation никогда не интерпретируется как исполнительное ребро Flow Editor.

### Доски, проекты, навигация и поиск

- **R-26.** Пользователь создаёт несколько независимых досок.
- **R-27.** Для каждой доски сохраняются placements, viewport, слой, display state и открытые элементы.
- **R-28.** Проекты создаются, переименовываются, закрепляются, отображаются иерархически, архивируются и восстанавливаются.
- **R-29.** Навигация содержит «Новый чат», «Поиск», «Запланировано», «Автоматизации», «Проекты» и создание доски.
- **R-30.** Единый поиск охватывает разрешённые пользователю чаты, доски, проекты, заметки и автоматизации.
- **R-31.** Раздел «Запланировано» показывает правила, следующий запуск, предыдущий результат, состояние и управление расписанием.
- **R-32.** Раздел «Автоматизации» показывает список существующих Automation и открывает полноэкранный Flow Editor.
- **R-33.** Настройки открываются через аватар в одном компактном меню без дублирующего пути к тем же действиям.
- **R-34.** Ненужные служебные и legacy-элементы UI удаляются только после инвентаризации использования и миграции маршрутов.
- **R-35.** Канвас, окна, навигация, Automation и настройки используют общую систему токенов, состояний, focus/keyboard и accessibility.

### Надёжность, аудит, безопасность и совместимость

- **R-36.** После перезапуска восстанавливаются активные Project/Board, viewport, placements, история Chat и открытые Automation.
- **R-37.** Создание, изменение, запуск, результат, AI-preview, подтверждение, отказ и rollback Automation журналируются.
- **R-38.** Просмотр, изменение и запуск чатов, досок, проектов и автоматизаций контролируются отдельными действиями RBAC.
- **R-39.** Внешние, необратимые и рискованные действия компонентов ограничиваются policy/capability и требуют подтверждения по классу риска.
- **R-40.** Сохраняется совместимость с существующими Flow Editor, компонентами, API и KFX/LFX; изменения контрактов версионируются.

## 5. Контролируемые AI-команды

AI может формировать команды для Project, Board, Placement, Chat, Note, Automation, Schedule, поддерживаемых Settings и других явно зарегистрированных типов. Каждая команда должна содержать:

1. `command_type` и версию schema;
2. `actor_id`, workspace/project scope и источник (`ui`, `assistant`, `mcp`, `api`);
3. типизированные параметры без произвольного backend path;
4. `idempotency_key` и ожидаемую revision;
5. preview с diff, оценкой риска и обратимостью;
6. одноразовый confirmation token, если требуется;
7. результат, affected IDs, before/after revision и audit ID;
8. явное описание partial/compensated outcome для внешних эффектов.

## 6. Нефункциональные требования

- **NFR-01 — целостность:** конфликтующие записи не должны молча перетирать состояние; используется optimistic concurrency.
- **NFR-02 — восстановление:** после disconnect/restart состояние получает проверяемый terminal или recoverable status.
- **NFR-03 — доступность:** все основные операции доступны с клавиатуры; focus не должен уходить во вложенный canvas без явного входа.
- **NFR-04 — производительность:** тяжёлые окна монтируются лениво; offscreen content допускает виртуализацию/suspension.
- **NFR-05 — наблюдаемость:** stream/command/execution имеют request ID, sequence, duration, outcome и редактированный audit payload.
- **NFR-06 — локализация:** ru/en parity, plural/interpolation parity и отсутствие нового hardcoded system-owned English.
- **NFR-07 — совместимость:** сохраняется corpus legacy Flow; компонентные class names и extension manifest ABI неизменны.
- **NFR-08 — безопасность:** custom code и внешние интеграции рассматриваются как недоверенные; AST scan не заменяет sandbox/egress policy.
- **NFR-09 — данные:** SQLite поддерживается для локального режима, PostgreSQL — для production-like concurrency; различия проверяются тестами.
- **NFR-10 — откат:** feature flags и backward-compatible data path позволяют отключить новый UI без потери новых данных.

## 7. Дизайн-требования из референсов

Референсы задают желаемый UX, но не технологию реализации:

- точечный фон и пространственная ориентация;
- плавающие карточки разных типов;
- mini-map и zoom controls;
- различимые selected/focused/streaming/error states;
- отдельные chat, workflow, browser-like и note surfaces;
- быстрый нижний launcher/dock как гипотеза навигации;
- card header actions, resize и fullscreen affordance.

Требуются адаптация к дизайн-системе Ketos, ru/en, WCAG, keyboard/focus и responsive-поведению. Пиксельное копирование OpenSwarm не является требованием.

## 8. Гипотезы и открытые вопросы

- **H-01:** один полнофункциональный Flow Editor и несколько read-only/compact Automation windows дадут лучший баланс, чем несколько одновременно смонтированных редакторов.
- **H-02:** внешний canvas выгоднее реализовать отдельным DOM/window compositor, а не вложенным XYFlow, если semantic links можно отрисовать отдельным слоем.
- **H-03:** существующий `Folder` может остаться persistence-основой Project через совместимый API-адаптер.
- **H-04:** MCP полезен как внешний адаптер после появления Command Gateway, но не как внутренняя бизнес-граница.
- **H-05:** Message можно мигрировать к `chat_id` через dual-write, сохранив `session_id` как compatibility alias.
- **OQ-01:** допустимое число одновременно активных streaming chats и тяжёлых Automation windows.
- **OQ-02:** требования к совместному редактированию: optimistic lock достаточно либо нужен realtime collaboration/CRDT.
- **OQ-03:** поддерживается ли browser card в web-приложении; какие URL/capabilities допустимы.
- **OQ-04:** требуется ли schedule engine в первом релизе либо только отображение уже существующих запусков.
- **OQ-05:** какие внешние компоненты относятся к классам `review`, `confirm_each_time`, `deny`.
- **OQ-06:** какой corpus production-like Flow и Message доступен для миграционных/performance тестов.
