# Agent Note: Board window preset and model selection — defaults, catalog, and refusals

Status: implemented

English | [中文](2026-09-19-ketos-board-presets-models.zh.md)

## Problem

Stage 4 put the agent-preset and model chips into the window composer, but the selection surface stayed an early prototype. Stage 10's live audit found the window's model chip reading "no model selected" with an empty model menu while the main panel listed the model: the board never declared `remote.session`, and `ui-model-selection` resolves the host catalog through the caller's context, so `ModelDirectoryResolver` threw `cannot get property "remote.session" without inject` and the per-session directory published nothing — the failure was invisible because the board never rendered `BoardModelState.error`. The window's preset roster was fetched once per bridge and cached for the process, offered rows that the host marks `broken`, and ignored the deployment's `modeSelectionEnabled` policy. No window remembered a preset: every new window composed whatever the deployment defaulted to, so the user's pick on one window never reached the next, and the board stored nothing about it. A refused switch (`agent-preset/locked` and kin) surfaced as the host's raw `code: message` appended to the generic prompt-failure line, and the model chip's real side effect — `remote.session.selectModel` saving the choice as the `agent-default-model` system default — was stated nowhere.

## Decision

**The board declares `remote.session` because the model directory reads the host catalog through the caller's context.** `ModelDirectoryResolver.directoryFor(sessionId)` runs behind the caller-context tracker, so the per-session `ModelDirectory` can only resolve `remote.session.modelCatalog()` when the calling plugin's inject names that namespace. With `remote.session` in the board's inject list, the window's directory publishes the catalog groups, the current selection, and the reasoning-effort table, and the chip reads the model in force. This is also why the failure had been invisible: the bridge caught the throw into `model.error`, which nothing rendered. The model menu now shows that error as its own row and the window keeps working — a catalog failure is a menu-level condition, not a composer block.

**The board remembers its preset default.** `defaultPreset` is a field of the `ui-board` settings section (schema, store, capture, and repair), and the bridge applies it when it creates a window's or chat's fresh session: a `create → select` pair guarded by the session being blank and by the selection already matching. Every successful pick — the composer chip or the Omnibox's creation submenu — is remembered through the same field, so the last choice becomes the default for the next window and survives a reload with the rest of the layout. A default the host refuses is reported like an explicit pick rather than silently ignored: the deployment may have dropped the preset the user remembers choosing.

**The roster is read per attach and carries its policy.** The bridge no longer caches the roster for the process: a deployment can change its roots at any time, and a stale roster would offer rows that no longer compose. Rows keep the host's `broken` reason and `isDefault` marker in the window channel — a current preset still resolves its label — while the composer's menu and the Omnibox's creation submenu never offer a broken row. The roster's `modeSelectionEnabled` policy gates visible selection: with it false the window hides the preset chip and the Omnibox drops its Preset entry, because a control that cannot act is worse than none.

**Preset refusals are localized by code, and the model chip states its side effect.** `agent-preset/locked` renders as the "create a new session to change the preset" reason, `agent-preset/not-found` as the missing-preset reason, `agent-preset/invalid` and `agent-preset/read-only` carry the host's own reason, and an unknown code stays verbatim; the line renders under the composer beside the chip that caused it and clears on the next pick. The model chip's tooltip names the model and the reasoning effort in force and states that a switch is saved as the system default for new sessions, so the chip's scope is honest; picking a model calls only `selectModel`, so the preset in force never changes under the user.

## Alternatives considered

- **Leave the window without a preset default.** Rejected: the plan asks new windows to start with the chosen preset, and without a stored default every window silently composes the deployment default, which makes the composer chip's pick a per-window gesture the user must repeat.
- **Apply the default to every session the bridge binds, including restored and rebound chats.** Rejected: a started session's composition is fixed by design (the host locks it), and re-selecting on rebound chats would either fail or, worse, change the composition of a conversation the user resumed.
- **Keep the roster cached on the bridge.** Rejected: it is small, it is read on attach, and a process-lifetime cache keeps offering presets a deployment has since removed — the live roster in this stage already differs from the shipped default set.
- **Hide broken rows from the channel.** Rejected: the current preset's label resolves through the roster, and a session composed from a now-broken preset must still name it.
- **Render the model catalog error as a persistent composer line.** Rejected: the error belongs where the user can act on it (the model menu), and a catalog outage is transient while the window stays usable.
- **Keep the host's raw failure text for preset refusals.** Rejected: the plan asks for distinct localized causes, and `agent-preset/locked` is the common one — it needs the remedy, not the code.

## Consequences

A new window now starts with the preset the user last chose, the window's model chip shows the real model with an honest warning about the system default, a preset that cannot compose a session is never offered, and a refused switch explains itself in the user's language. The accepted costs: the remembered default is board-wide rather than per project or per window kind; the quick pick at creation lives in the Omnibox rather than as a step in the chats panel; with `modeSelectionEnabled` false the board loses the chip entirely instead of showing it disabled; and the model chip's menu error is the only place a catalog failure is named, so a user who never opens the menu sees the previous selection without an explanation.
