# Agent Note: The Ketos peer channel

Status: implemented

English | [中文](2026-10-06-ketos-peer-channel.zh.md)

## Problem

The 16 October demonstration runs two Ketos instances on two computers in different networks and presents them as one team: they must find each other through infrastructure the team controls, exchange messages reliably, show each other as real participants instead of the client-side demo roster, and recover a dropped channel without a new invitation. Board document synchronization, foreign chat cards, and a shared Syncthing folder run on top of this channel, so its service surface, frame codes, and event names are defined once, here.

## Decision

**One iroh node per Ketos behind `ctx.ketosPeer`.** `@ketos/peer` binds an iroh endpoint with a 32-byte key stored at `$DSH_HOME/peer.key` (owner-only, stable `EndpointId` across restarts), the peer ALPN `ketos/peer/3` (protocol version 3: a node on another version cannot connect), and `RelayMode.customFromUrls` over the team's private relay. Public n0 relays and discovery are never used; the deployment runs its own `iroh-relay` (Let's Encrypt via `<ip-with-dashes>.sslip.io`, fallback `nip.io` or `--dev`) in `docker/relay/`. The node starts lazily — on the first route call, or at plugin start when `peers.json` already names someone — so a developer machine that never composes the stand never loads the native module.

**Framing and extension belong to the channel; payloads to its consumers.** One connection carries one bidirectional QUIC stream; every message is `[u32 BE length][u8 code][body]`. The code table reserves `1 hello`, `2 bye`, `3 board.sv`, `4 board.update`, `5 chat.transcript.request`, `6 chat.transcript.response`, `7 syncthing.device`, `8 peer.ping`, and `9 peer.pong`; consumers merge their payloads into `PeerFrameTypeMap` through declaration merging and register handlers with `ctx.effect`. A frame over `maxFrameBytes` (16 bytes for the heartbeat codes), a non-JSON body, an unknown code, or a truncated frame closes the connection with code `2n` without throwing past the read loop. Requests and responses share one envelope (`{ requestId, request }` / `{ requestId, response | error }`), with the timeout on the asking side.

**A heartbeat bounds how long a broken path stays unnoticed.** iroh-js 1.1.0 exposes no idle-timeout or keep-alive setting, so without more only QUIC's idle timeout, about 30 s, ends a silently broken path. Each link therefore sends `peer.ping` every `heartbeatIntervalMs` (3 s by default) whatever else it sends, and answers every ping with `peer.pong`; both bodies are exactly `{}`. A completed read, a frame header or a body slice of up to 16 KiB, restarts the countdown of `heartbeatTimeoutMs` (9 s by default), so board traffic keeps a link open and a large update keeps it open while each slice arrives within the timeout. When the countdown expires, the link decides one event-loop turn later, so bytes that arrived while the event loop was blocked count; otherwise it logs one `peer.heartbeat-timeout` line and closes with reason `heartbeat-timeout` (code `6n`) without a `bye`, the peer turns `lost`, and the dialing side redials as after any other loss. The board shows the peer as not connected at most `heartbeatTimeoutMs` plus one `stateRefreshMs` poll after the last completed read. Pings are unconditional and every ping is answered, so each side's detection depends only on its own two values; the plugin refuses a load where `heartbeatTimeoutMs` is below twice `heartbeatIntervalMs`. The heartbeat codes exist from protocol version 3, and builds of other versions use another ALPN and do not connect.

**The invitation code admits exactly one unknown node.** `invite()` waits for the relay address and mints `ketos1.<endpoint ticket>.<base32 secret>`; the 16-byte secret is single-use, memory-only, and valid for `inviteTtlMs`. The dialer writes `hello` first (the receiver's `acceptBi` resolves only after those bytes) with its participant record and, for an unknown node, the secret. A node already stored in `peers.json` is admitted without a secret; an unknown node with a wrong or absent secret is closed with code `1n` and one `peer.refused` log line. The first frame of either side is bounded to 4096 bytes, an unknown node's secret is compared in constant time, and five wrong secrets burn the invitation. The dialing side stores the peer's ticket and owns reconnection (pauses from `reconnectMinMs` to `reconnectMaxMs`, doubling with ±20% jitter and never above `reconnectMaxMs`); a link that lived shorter than `reconnectMaxMs` counts as a failed attempt, so a link that keeps closing right after the handshake backs off instead of redialing every second. The accepting side stores the record without a ticket and waits for the redial; an authenticated new connection from a known node replaces its old link (close code `5n`), so a half-dead link never blocks the redial. When both sides dial at once — each holds a ticket after both pasted codes — both keep the connection dialed by the node with the smaller endpoint id, so simultaneous dials never cost both links. A known node that is offline can be forgotten with `POST /api/ketos.peer.forget`.

**Participants are document records, one writer each.** `@ketos/board-doc` keeps a `participants` `Y.Map` keyed by `OwnerId`; `putOwnParticipant` writes only the record its own `selfId` keys, so board document synchronization cannot make two instances overwrite each other. The color is the first free palette number among the document's participants and the known peers; on a collision the participant with the larger board `selfId` (string comparison) rewrites its own record to the next free color and announces a new `hello`, while the other side keeps its record untouched. The browser roster unions the document records with the peer channel's state, so both boards show two real participants whether or not the document has synchronized yet.

**The profile row is disabled; the stand enables it.** The shipped `web` profile carries `ketos-peer` with `disabled: true` and only the environment seam (`KETOS_PARTICIPANT_NAME`, `KETOS_RELAY_URLS`), because identity and relay exist only on the stand; `docker/stand/stand.patch.yml` enables the same row with the deployment's values and caps the reconnection pause at 5 s and the dial timeout at 5 s (`reconnectMaxMs: 5000`, `connectTimeoutMs: 5000`; package defaults 20 s and 10 s), because a pause of up to 20 s plus a dial that times out at 10 s can exceed the 30 s within which a link has to be back after the network returns, and a dial started while the iroh relay connection is still reconnecting waits out its whole timeout while measured dials take 0.5 to 1 s. The client polls `/api/ketos.peer.state` only while the board surface is rendered and its tab is visible, and stops after an unavailable (404) answer, so a deployment without the plugin produces no background 404 traffic.

**iroh-js 1.1.0 forbids `watch*` and `stopped()`.** The pinned version aborts the Node process on any `watch*` call and never resolves `SendStream.stopped()`; both are banned by `tests/native-surface.spec.ts`, which scans the sources, and address changes are observed through the relay `online()` wait and the connection's `closed()` promise instead. The ban lifts when the pinned version is raised past the crash and the gate is updated with it.

**The stand's Syncthing is pinned and private.** Debian's 1.19.2 predates relay tokens and joined public relays; the image installs the official 2.1.5 archive, verified by sha256 per architecture, and `syncthing-bootstrap.mjs` edits the generated `config.xml` on every start before Syncthing runs — global and local announce off, NAT off, crash reporting off, no STUN, no auto-upgrade, a 10 s reconnection interval (`reconnectionIntervalS`, stock 20 s), a 1 min relay reconnection interval (`relayReconnectIntervalM`, stock 10 min), `listenAddresses` = the team's `strelaysrv` URL and `tcp://0.0.0.0:22000`, GUI API key from `STGUIAPIKEY`. A template drift or a missing relay fails loud. `run-with-redacted-log.sh` rewrites the relay token in Syncthing's output before a line reaches its log file; the GUI keeps the token in its in-memory log and options and has no password until after the demonstration, so the stand publishes it on `127.0.0.1` only. How the two Ketoses link their Syncthings over frame `7` is in [Syncthing over the iroh channel](2026-10-09-ketos-syncthing-over-iroh.md).

## Alternatives considered

- **Public iroh relays and discovery.** Rejected: the demonstration must not depend on n0 infrastructure, and a private relay also makes the address stable and auditable.
- **A hand-rolled TCP/TLS channel.** Rejected: NAT traversal, QUIC multiplexing, connection migration, and endpoint identity are exactly the hard parts iroh already provides; the transport seam keeps the rest of the channel testable without it.
- **Per-person rights and a signed participant list.** Rejected for the demo: any known peer's frames are accepted, and the channel protects against outsiders, not against a known peer; rights arrive after the demonstration.
- **A separate client plugin package for the participants menu.** Rejected: the menu is board chrome; it lives in `packages/client/ui-board` beside the dock, and the peer API is a plain route client like `board-doc-api.ts`.
- **Relying on QUIC's idle timeout.** Rejected: iroh-js 1.1.0 offers neither a shorter timeout nor keep-alive, so a silently broken path would stay unnoticed for about 30 s, while the board has to show a lost peer within seconds.
- **Skipping pings after recent traffic, or pinging only when nothing arrived.** Rejected: with skipping, a side whose outgoing traffic never stops sends no pings and its detection depends on the other side's cadence; a ping that waits until nothing arrived queues behind a large outgoing write. Unconditional pings with a pong for every ping cost a few small frames per interval and make each side's detection depend only on its own two values.
- **Counting only whole frames as a sign of life.** Rejected: one large `board.update` that takes longer than `heartbeatTimeoutMs` to arrive would close the link at every initial synchronization on a slow path, and the redial would repeat it. Counting each completed read keeps such a link open while the path carries about 14.6 kbit/s with the defaults.
- **Starting the poll at plugin load.** Rejected: a deployment without the peer plugin would issue one 404 per second forever; the board surface reports its own mount, and an unavailable answer stops the loop.

## Consequences

A connection is established through the team's relay (the link may move to a direct path afterwards): if the VPS is down, no new peer connection can be established, and `invite()` answers 503 `ketos/peer-offline` until the relay address exists. `peers.json` is the only durable state besides the key, so a deleted file loses the known peers and requires a new invitation code. A failed handshake of one incoming connection never stops the accept loop. The accepting side cannot redial, so after both sides restart the originally dialing side reconnects from its ticket. The native module ships no `darwin-x64` build, so an Intel Mac runs the channel only inside the Docker stand. The frame table reserves codes before their consumers exist; a reserved frame without a handler is ignored with one log line, so a missing consumer never costs the connection. Both Ketos instances of a pair run the same protocol version: every version has its own ALPN and no fallback exists.

The heartbeat bounds detection, not recovery: after the network returns, the dialing side's next dial waits for the pause in progress, up to `reconnectMaxMs`, and a dial in flight may first run into `connectTimeoutMs`, so with the defaults both sides may take up to about 10 + 20 s plus the dial itself to show `online` again. The stand caps the pause and the dial timeout at 5 s for that reason, which bounds recovery at a pause of up to 5 s, a dial that may time out at 5 s, another pause of up to 5 s, and the dial itself. A path slower than about 14.6 kbit/s cannot carry a frame over 16 KiB: the link closes with `heartbeat-timeout` during the transfer and the redial repeats the exchange.

## Testing

`packages/ketos/peer/tests` covers the protocol over the in-memory transport (frames, handshake, refusals, known peers, participants and the color rule, request timeouts, reconnection with fake timers and cancellation), its heartbeat (ping cadence, a pong for every ping, the close exactly at `heartbeatTimeoutMs` with one log line, liveness from board traffic, pongs, and every slice of a large frame, timers cleared at close), and the transport itself on two loopback iroh endpoints; the Loader composition suite boots the real plugin, proves the stable `EndpointId` through the key file, and rejects a wrong-length key. Coverage is 100% per file. `packages/ketos/board-doc/tests/participants.spec.ts` covers the participant map and record validation at 100%. The client suites cover the peer API decoders, the poll lifecycle, the roster union, and the participants popover; the live stand check connected both boards in 0.08 s through the VPS relay and restored the link 2.8 s after restarting one container.
