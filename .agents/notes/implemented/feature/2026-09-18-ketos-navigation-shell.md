# Agent Note: Navigation shell — dock status, Omnibox delivery, inspector chip

Status: implemented

English | [中文](2026-09-18-ketos-navigation-shell.zh.md)

## Problem

Stage 6 completed the chat window, but the four surfaces around it were still stubs. The dock listed windows by name and centered them, yet it knew nothing about their sessions: a window that was creating, running, or broken looked like every other row, and the only way to close one was its frame. The Omnibox was not wired to a session at all — Enter cleared the field, and the attach, dictation, and web-search entries silently closed the menu — and no board surface could open a tool window even though `WindowFrame` had served all six kinds since stage 4. The element-selection overlay drew its frame and pill, but a click did nothing: there was no capture format and no path into a window's draft. Layer consistency had two loose ends: the chats panel's overlay presentation sat inside the canvas transform, whose stacking context caps it below the root-level chrome, so the Omnibox could paint over the panel's bottom edge (`ketos-0iy`), and board popovers each computed their own side and alignment.

## Decision

**The dock reads the same window channel as the frame, and its rows act on the store.** Every row resolves the title through `windowTitle` and the status from the keyed `useWindowSession(windowId)` seat that the frame already uses, so one channel serves both surfaces and no component subscribes on its own. The status is the session fact the channel owns: a missing or pending session reads creating, a creation, prompt, or turn failure reads error before a running turn does, a running turn reads running, and every other ready session reads idle; `StateDot` renders it and `rail.statusLabel` pairs the localized status with the title for the accessible name. Clicking the active window's row only focuses it — the view has already been centered on it — while any other row centers and focuses. The row's context menu (`onContextMenu`, the shared portalled `Menu`) renames through the existing in-place editor or closes the window, and the close entry states that the chat stays listed, because that is what happens: the window leaves the store, the windows layer releases the bridge record, and the session stays alive. The dock's `+` keeps its one-click agent add; its context menu opens the same kind catalog the Omnibox carries, so both chrome surfaces can create windows of the kinds stage 7 owns.

**One addressing rule serves every board-chrome command.** `open-window.ts` resolves the window a command acts on: the active chat window when there is one, otherwise a freshly opened agent window at its template size. The Omnibox's send and the inspector's chip both go through it, so neither surface invents a fallback. Delivery goes through the window bridge rather than a private session path, and the bridge now waits for the window's session creation (`whenReady`) before sending: the Omnibox can open a window and submit in the same gesture, before the new composer has mounted and created the session. A window closed while its session was being created stays closed — the bridge checks that the record still exists before binding.

**The Omnibox replaces every stub with a real action or an explicit reason.** Enter trims the draft and queues it into the addressed window's session. The `+` menu's New window section opens agent, connectors, and settings windows from `BOARD_WINDOW_TEMPLATES`, creates a clone and opens its editor window, and answers dashboard and tasks with the localized unavailable notice the plan allows, because those surfaces belong to later stages; a Clones section lists the stored records and opens — or brings forward — their editor windows. Attach file routes a file-picker command through the composer-intent queue; Dictate toggles `useDictation` into the Omnibox draft and reports an unsupported browser; Web search states that the `web` capability is host-side with no client path, which is the client's honest boundary, not a missing wire; Select an element enables the inspector. The menu is portalled and shares one placement rule with every other board popover (`menu-placement.ts`), so a list opens on the roomier side wherever its trigger sits.

**The inspector captures a deterministic description and inserts a plain-text chip through the composer.** `element-capture.ts` builds a `tag:nth-of-type(n)` selector anchored at the nearest board surface (or `body`) and a language-neutral description of the stable facts: tag, containing window kind and title, `data-board-action`, accessible name, tooltip, and a 60-character text excerpt. The overlay's layer already passed pointers through, so the capture runs on a capture-phase click listener: it exempts clicks inside its own pill, stands down while a menu is open (the same precedence Escape uses), claims only clicks inside the board surface so the app's own chrome keeps its meaning, and suppresses the default action so the control under the pointer never activates. The pick becomes one `ComposerIntent` addressed by `resolveChatWindow`; the addressed composer consumes intents — text appends to the draft, a file-picker command clicks the file input only once the composer can accept files, and closing a window drops its queued commands so the queue cannot grow orphans. The composer has no editor chips (the stage-4 limitation), so the chip is draft text the user can edit or delete like any other mention.

**An open chats panel stands the whole floating chrome down.** `ketos-0iy` is resolved by consistency rather than by moving the panel: the panel stays a layer of the canvas transform, where its geometry, scaling, and menu behavior already work, and the root-level chrome — dock, Omnibox, and minimap — stops rendering while the panel is expanded, exactly as the dock and minimap already did. Nothing is left for a root-level layer to cover: the panel's outer edge, its resize handle, and the window's bottom edge in the overlay presentation are all reachable, and the fullscreen frame already stood the chrome down the same way. The ladder in `BoardViews.tsx` and the README state this final rule.

## Alternatives considered

- **Move the chats panel to a root-level, screen-space layer like the handle ring.** Rejected: the panel's width, height, and typography would stop scaling with the canvas zoom, its documented world-unit geometry and every panel-geometry test would be rewritten, and its menus would need a second placement path — a large behavioral change for a P3 overlap that the chrome stand-down resolves without touching the panel. The panel keeps its transform layering and its documented following behavior.
- **A visible per-row close button in the dock.** Rejected: the rail is a 38px icon column; a second control per row would crowd the status glyph it exists beside, and the row menu keeps the rail compact while carrying the rename entry next to close. The close label's hint tells the user the chat survives.
- **Send the Omnibox text through `ctx.sessions` directly.** Rejected: that duplicates the queue/steer policy and the session-creation ordering the window bridge owns; the bridge is the one path that also serves the composer, and its `whenReady` wait is what makes Open-then-Send reliable.
- **Call a `web_search` tool through the addressed session.** Rejected: the menu entry carries no query and the `web` service is a host capability the client plugin cannot inject; an explicit localized reason is the honest outcome the plan allows, and a hidden prompt would spend a model turn the user did not ask for.
- **Capture the selector only.** Rejected: the model can locate a node by selector but cannot tell what it is; the description's window kind, title, action id, and text excerpt are what make the chip actionable, and each part is a stable DOM fact rather than localized copy.
- **Editor chips for the inspector capture.** Rejected for the same reason stage 4 rejected editor chips for `@` mentions: the board composer is a textarea, not the conversation package's editor, and a chip component would need an editor slot the package does not define.

## Consequences

The board chrome now tells the truth about every window, and the three previously stubbed Omnibox entries either act or say why they cannot. The inspector closes the loop from the canvas to a model prompt: a picked element becomes editable draft text in the addressed window's chat. The accepted costs: window status stays a coarse four-state projection with no per-tool progress; the chip is draft text, not a removable editor chip; Web search and the dashboard and tasks windows report unavailable in this MVP; and while a chats panel is open the Omnibox is not reachable, so a user who wants to open a window or inspect an element collapses the panel first (the panel's rail keeps that one click away). `ketos-md8` (tool-window templates) and `ketos-0iy` (panel below the chrome) are closed by this work. The board still injects exactly the stage-6 service set: `minimap.aria` needed only the `locale: NS` registration on the existing minimap entry, and no new package, manifest, or generated catalog changed.
