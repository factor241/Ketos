# Agent Note: Ketos board synchronization

Status: implemented

English | [中文](2026-10-06-ketos-board-sync.zh.md)

## Problem

Stage 33 makes two Ketos boards one shared board: elements, participants, and window records must appear on the other instance in the owner's color within a second, concurrent edits must converge, edits made while a channel was down must catch up after it returns, foreign content must be read-only, and data whose owner is disconnected must be marked. The channel (`@ketos/peer`) and the document (`@ketos/board-doc`) already exist; the synchronization had to be split between them so neither learns about the other's mechanics, while stages 34–35 build transcript cards and a shared folder on the same seams.

## Decision

**The document is the shared state; the channel carries only Yjs updates.** `@ketos/board-doc` exposes `stateVector()`, `diffSince(vector)`, `applyRemote(update)`, and `onLocalUpdate(listener)` and knows nothing about the channel; `@ketos/peer` owns the schedule in `src/board-sync.ts`. On every `ketos-peer/connected` — the first connection and each reconnection — each side sends its state vector (`board.sv`) and answers the other's vector with `diffSince` (`board.update`); every transaction the document produces is relayed to each connected peer. Remote updates apply with the `peer` transaction origin, which the relay rejects, so one change is exactly one frame and there is no echo.

**Binary frame bodies, one writer per record, and a sender-side bound.** Codes `3 board.sv` and `4 board.update` carry raw, non-empty `Uint8Array` bodies: `JSON.stringify(Uint8Array)` would produce an object five to six times larger and could never be restored, so the frame vocabulary treats these codes as binary and keeps JSON and the request/response envelope for every other code. `decodeUpdate` validates the bytes before they reach the document, so an unreadable update refuses with `BoardSyncError` and changes nothing; a handler exception is logged and the channel stays alive, because an apply failure must not send the peer into a reconnect loop. `send` encodes and measures a frame before queueing it, and an update over `maxSyncUpdateBytes` (15 MiB) is never sent: the line `board.sync.too-large` goes to the host log and the channel closes with code `4n`. Each record has one writer — an element only its owner, a participant only its own `selfId`, a window record only the Ketos that hosts it — which is what makes last-writer-wins per field sound.

**A patch writes only the fields it changes.** `BoardDocument.patch` skips every value the document already holds. Until this stage it rewrote the complete envelope, so two Ketos instances patching different fields of one element concurrently clobbered each other; now the nested per-key maps deliver the merge they were designed for, and the plan's yjs experiment (`x` on A, `text` on B converging to `{ x: 100, text: 'changed' }`) holds over the channel.

**Window records are a `windows` map, not elements.** A record is `{ id, hostId, ownerId, kind, bodyKind, title, ordinal, x, y, w, h, z, access, status, sessionId?, updatedAt }`; the host stamps `hostId = selfId` and `updatedAt`, a browser write naming another `hostId`, or targeting a record another Ketos published, refuses with `ketos/window-foreign` (409), and the record budget is `maxWindowRecords` (100). Snapshots and patches carry a `windows` slice beside elements and participants, so the browser learns records over the stream it already follows; the records never enter the element map, the layout, the dock, or the overview.

**The visible tab publishes this browser's windows; receivers render placeholders.** `window-publish.ts` posts one `window.put` per changed window after a trailing debounce (place, size, title, owner, access, or session status — not `z`, so focusing a window does not publish; the title is the window's own name, else the clone's name, else the chat title, cut to the record's title bound). Removal has a single source: a reconciliation that deletes own records the stored layout no longer holds, run only by the visible tab, never for a window whose put is still in flight, and only once the layout's source is known (`layoutSource`): a layout adopted from the settings server lets it delete every own record without a window, so a fresh profile never deletes records its empty layout has not loaded and a record left by a closed browser is cleaned up; a layout held in memory (a page outside loopback) deletes only records this publisher put itself. Two visible tabs whose layouts diverge can still delete each other's records; republishing on removal would make them fight, so that stays a documented limitation. A refused operation is not posted again until its record changes, except `ketos/limit`, which is retried once the document holds fewer records, an unreachable host is retried after `windowPublishRetryMs`, and one bad record never blocks the others. A hidden tab keeps its pending changes until it returns. `ForeignWindowLayer` renders other Ketoses' records between the elements and the local windows, culled by the visible rectangle and painted by the record's `z`, through `WindowBezel` with the owner fill and no menus, drag, or handles, wrapped in a placeholder body that the keyed `board.foreign.window.body` slot can replace per window kind (stage 34 registers the chat card). `canManageWindow` requires the window to be in this Ketos's layout, so a record another Ketos published is never manageable here even when its `ownerId` names the acting participant. A `peer.stale` mark appears on the elements and windows of a known owner none of whose peer entries is `online` (`connecting` included), with a focusable hint that the data may be out of date; a deployment without peer networking, or an owner the roster does not know, is never marked.

## Alternatives considered

- **JSON or base64 frame bodies.** Rejected: JSON inflates a yjs update roughly fivefold and does not round-trip a `Uint8Array`; base64 would still inflate by a third and add conversions on both sides of every change.
- **A full snapshot on reconnect instead of a state-vector exchange.** Rejected: the exchange is incremental, bounded by what the other side misses (8 bytes for a state vector, tens of bytes for one changed element in a 300-element document), and already exercised by the connection path.
- **Closing the channel on any handler exception.** This was the stage-32 behavior; rejected because a remote update this build cannot read would cost the connection and produce a reconnect loop — the failure belongs in the log.
- **Storing window records as elements.** Rejected: records have a different lifecycle (published, reconciled, one writer per host), do not belong in the element budget or the element paint order, and must not be movable by a receiver.
- **Publishing windows on every `z` change.** Rejected: raising and focusing a window would publish constantly, and the receiver only needs an order to paint placeholders; the record keeps its `z` from the last real publish.
- **Writing the complete envelope on every patch.** This was the stage-28 behavior; rejected after the concurrent-edit test showed a move on A and a text edit on B ending at whichever complete envelope landed last. Writing only changed fields restores the per-key merge the nested maps were built for.
- **Marking only `lost` as stale.** Rejected: the dialing side sits in `connecting` between attempts, so the mark disappeared while the data was still old; any state other than `online` means no channel carries changes.
- **Splitting an oversized update into fragments.** Rejected: Yjs 13.6 applies partial updates poorly, and the showcase board is about 3.5 MB against the 15 MiB bound; an oversized board is a logged close with a backed-off reconnect instead.

## Consequences

Two boards are one board: an element, participant, or window record written on one appears on the other in the owner's color (measured 16 ms median in the stand), simultaneous edits of different fields merge, and edits made while the channel was down are exchanged by the next connection's state vectors (measured 0.04 s after both peers reported online). A board larger than `maxSyncUpdateBytes` closes the channel with a log line instead of sending — the bound is far above a normal board because strokes are rounded. A foreign window is a placeholder with the owner's bezel fill; managing a transferred window from the receiver, live chat over the network, and per-person rights are out of scope for this stage.

## Testing

`packages/ketos/board-doc/tests/sync.spec.ts` covers the state-vector exchange, the local-update relay (remote and `load` replay never reach it), journal persistence of a remote update, repetitions, and malformed bytes at 100% coverage; `tests/windows.spec.ts` covers record validation, publish/change/remove, the foreign-host refusal, the budget, unreadable records, and the remote exchange. `packages/ketos/peer/tests` covers binary frames both ways, the sender-side size check, the handler-failure containment, the connection exchange with participants, echo-free relay, simultaneous edits, the too-large close, the reconnect catch-up, and 100% coverage. The client suites cover the publisher (one put per burst, status from the channel, removals, visibility gating, reconciliation, retry), the foreign layer (owner color, no controls or handles, culling, records outside layout/dock/overview, the locality predicate), the stale marks, and the minimap rects. The live stand verified window open at 26.7 ms and move at 43 ms, `sync-latency.mjs` measured 20 notes at 16 ms median / 31 ms max, and stopping one container showed the `Нет связи` marks on the other before the offline edits converged.
