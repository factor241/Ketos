# Agent Note: Syncthing over the iroh channel

Status: implemented

English | [中文](2026-10-09-ketos-syncthing-over-iroh.zh.md)

## Problem

The 16 October demonstration shows two Ketos instances on two computers in different networks working in one folder: a file that the model writes into `/workspace/shared` on one Ketos appears in the same folder on the other. Syncthing moves the files, and it needs three things from Ketos: the other instance's device ID, the folder shared with that device, and a rule that its traffic crosses only the team's private relay, with no public discovery, no NAT mapping, and no public relay pool. Done by hand, two people paste device IDs and a relay address into two web interfaces on two computers, and repeat it whenever a Syncthing volume is recreated. The linking therefore had to follow the invitation without manual steps, be safe to run again at every reconnection, follow a changed device ID, and keep Syncthing's network settings under one writer. A Ketos that has no Syncthing key still has to keep its channel and board synchronization.

## Decision

**The channel carries only the device ID; Syncthing's REST API does the configuration.** The feature is part of the `ketos-peer` plugin and is enabled by the optional `Config.syncthing` section, which the stand overlay `docker/stand/stand.patch.yml` fills (`url` `http://127.0.0.1:8384`, `apiKeyEnv` `STGUIAPIKEY`, `relayAddress`, `folderId` `ketos-shared`, `folderPath` `/workspace/shared`); without the section the feature does not exist. On every `ketos-peer/connected`, the first connection and each reconnection, a Ketos reads its own `myID` from its local Syncthing and sends it as frame `7 syncthing.device`, whose JSON body is exactly `{ deviceId }`. A received frame is applied to the local Syncthing through its `/rest/config` routes: first the device `ketos:<peer id>` with `addresses: [relayAddress]` and `autoAcceptFolders: false`, then the folder of type `sendreceive` with the watcher on (`fsWatcherDelayS`, 1 s in the stand). A device ID is accepted only in canonical form, eight groups of seven base32 characters whose 14th, 28th, 42nd, and 56th characters are Luhn mod 32 check characters and whose last data character has its four padding bits at zero, so that one device has exactly one accepted spelling; Ketos implements the check from the format description. A frame with any other body, and this Syncthing's own ID, is dropped with one `syncthing.device-invalid` line.

**The bootstrap is the single writer of Syncthing's network settings; Ketos only checks them.** `docker/stand/syncthing-bootstrap.mjs` edits Syncthing's `config.xml` on every container start, before Syncthing runs. Among its edits are global and local announcements off, NAT off, relays on, `listenAddresses` equal to `KETOS_SYNCTHING_RELAY` plus `tcp://0.0.0.0:22000`, a 10 s reconnection interval (`reconnectionIntervalS`, stock 20 s) so that Syncthing redials a lost peer device sooner, and a 1 min relay reconnection interval (`relayReconnectIntervalM`, stock 10 min) so that a relay connection that died is redialed within a minute. A missing element or a missing relay value stops the container. Ketos never writes these options. On the first poll after Syncthing answers, at feature start and again after Syncthing stopped answering, it reads `/rest/config/options` and compares them: announcements and NAT off, relays on, the private relay among the listen addresses (compared as URLs without `token`, with the query decoded and unordered), and no `default` or `dynamic+` listen address, which would join the public relay pool. A divergence sets the shared-folder state to `error` and logs one `syncthing.settings-diverge` line that names the settings and never an address. Linking continues, because peer devices are dialed only at the relay address whatever Syncthing's discovery settings are.

**Peer devices carry the relay address without its token.** The token admits a listener to `strelaysrv`; dialing a listener needs only the relay's address and ID. `stand.patch.yml` removes the `token` parameter from `KETOS_SYNCTHING_RELAY` before the value reaches the plugin, and the token stays in Syncthing's own listen address, which the bootstrap writes. Syncthing prints that address, token included, to its standard output at every start, so the stand starts it through `run-with-redacted-log.sh`, which rewrites `token=` values before a line reaches `/data/syncthing/syncthing.log` and ends Syncthing when its reader stops instead of letting an unredacted line through. A `syncthing.relayAddress` that is empty, is not `relay://host:port/?id=<relay device id>`, or carries `token` refuses the plugin at load. Load errors, host log lines, and request errors name fields, rules, request paths, and HTTP statuses, and never contain the API key, the token, or an address.

**Linking is idempotent, ordered, and serialized.** Every application of a received ID runs in one queue. The device is written before the folder, as a complete PUT body, because Syncthing builds a PUT from its defaults and resets the fields the body omits. The folder is created with a complete body when it is missing and otherwise PATCHed with the merged device list. A PATCH replaces `devices` whole, so the list is read, merged, and written inside the queue, and a second participant joins the folder without displacing the first. Devices compare by name, addresses, and folder acceptance, and folder device lists compare as sets without the own device; when everything matches, the application sends no mutating request. Each reconnection therefore costs reads only, and after a container restart Syncthing's configuration on its volume already holds the link. A write logs `syncthing.linked`.

**A new Syncthing ID replaces the old device.** A peer whose Syncthing volume was wiped announces another ID under the same Ketos identity. The previous device is found by its name `ketos:<peer id>`; it leaves the folder and the configuration (`syncthing.device-replaced`), so the device list does not grow. A newer ID from the same peer also supersedes an older frame that still waits in the queue.

**A forgotten peer's device leaves the folder.** `forget` emits `ketos-peer/forgotten` once the known-peer file no longer lists the peer. Every device named `ketos:<peer id>` other than the own device then leaves the folder and the configuration, in the same queue and with the same retries, and `syncthing.unlinked` reports it. Without this, a forgotten Ketos would keep syncing the shared folder in both directions. A refused removal stops with one `syncthing.link-stopped` line and leaves the device configured; a device ID the same peer sends after a new invitation ends a removal that has not run yet. While the feature is off, forgetting sends no Syncthing request.

**A reconnection after a long loss restarts Syncthing's connection to an unchanged peer device.** When the channel to a peer was lost for at least `kickAfterLostMs` (90 s by default) before it connects again, the first application of that connection whose peer device is already configured under the same ID pauses the device (`POST /rest/system/pause?device=<id>`) and then resumes it (`POST /rest/system/resume?device=<id>`), also when the pause failed, and logs `syncthing.reconnected`. In Syncthing 2.1.5 the pause closes the device's connections and the resume dials it at once. In a live run with a 120 s network cut, the relay session ended, yet B's Syncthing kept counting its dead relay connection to A as connected for about 84 s after the channel was back, so B reported the folder synchronized while a new file from A did not arrive. Shorter outages get no restart: Syncthing's relay connections survived cuts of 20–65 s, and Syncthing force-redials a device at most three times within 2 minutes and then holds off for 5 minutes. The loss is measured on the wall clock from `ketos-peer/disconnected` to the next `ketos-peer/connected`, so a first connection and a connection without a preceding loss get no restart. A first linking and a replaced device need no restart either, because Syncthing dials a new device by itself, and a frame the peer sends again on the same channel gets none. Syncthing stores the pause in its configuration, so the restart runs in the linking queue as part of the application step: a failed pause or resume fails the step, and a retry restarts again. Every application also resumes the peer device with one resume request and no restart when Syncthing reports it paused although it otherwise matches (`syncthing.device-resumed`); a device left paused by a failed resume or by a restart that a stopped Ketos interrupted is thus resumed at the next connection, and a device that is not paused costs no request.

**Syncthing and Ketos start in parallel, so the linking retries and stops by failure class.** No answer, a timeout, or a server error (5xx) from Syncthing, and any failure that is not a Syncthing error, such as a frame the channel could not send, retries the step every `retryMs` (2000 ms by default) with one `syncthing.retry` line. Any other Syncthing failure, such as a refused key (401, 403), another client error, a malformed answer, or an API key that was removed after the start, ends the step with one `syncthing.link-stopped` line, and the next channel connection starts both steps again. The peer's disconnection and plugin disposal end every step.

**The shared-folder state is polled, follows the Ketos channel, and is reported on the peer state route.** A monitor polls every `statusRefreshMs` (2000 ms by default), and `GET /api/ketos.peer.state` reads its latest result from memory as `sharedFolder`. The state is `unavailable` when Syncthing does not answer; `waiting` before the first poll, while the folder is missing or not running, while no peer device of the folder is connected, while no Ketos channel to the peer of a connected device is `online` whether the folder syncs or is idle, and while no peer with an online channel has its Syncthing sharing the folder back; `syncing` while the folder scans, transfers, or still needs items and the channel to the peer of a connected device is `online`, and while every peer with an online channel that shares the folder back still needs items or deletions; `synced` when it is idle, needs nothing, and a connected device of the folder carries the name `ketos:<peer id>` of a peer whose channel is `online` and whose Syncthing shares the folder back and needs nothing; and `error` when Syncthing refuses a request or answers malformed JSON, the API key is gone, the settings diverge, or the folder reports `error`. The peer's side comes from `/rest/db/completion` for its device: `remoteState` is `valid` once the peer's cluster configuration shares and runs the folder, and `needItems` plus `needDeletes` count what the peer still needs according to its index. The channel condition is read again from memory on every state read, so `syncing` and `synced` turn `waiting` as soon as the channel is lost, without waiting for the next poll, and turn back once the channel is online; `unavailable` and `error` do not depend on the channel. Syncthing keeps its own dead-connection timeouts and reported a silently lost peer as disconnected only 78 s after the cut in a live measurement, much later than the channel's heartbeat notices it, so the channel decides. The field is absent while the feature is off. A log line appears only when the reported condition changes.

**No key means no feature.** `apiKeyEnv` names an environment variable, read through the credentials service when the composition has one and from the launch environment otherwise, once at start and again before every request; no copy is kept. When the section is present and the key is not set at start, only the Syncthing feature stays off: one `syncthing.disabled` log line that names the variable and, when the key reader failed, says only that the key could not be read, never the reader's error text, no Syncthing request, no `sharedFolder` field, and the channel, board synchronization, and transcripts keep working. A key removed later turns the state to `error`. This is a deliberate exception to failing loud on misconfiguration: the key belongs to the Syncthing installation rather than to the channel, and refusing the plugin would take down a working channel because of an add-on. Invalid values of the section itself, such as a plain `http://` URL for a host that is not loopback, a user name in the URL, an unusable folder ID, or a relative folder path, still refuse the plugin at load.

**Syncthing stays a separate program.** Syncthing is MPL-2.0. The stand image installs the official 2.1.5 archive, pinned by sha256 per architecture, with its license text, and the entrypoint starts it beside Ketos. Ketos reaches it only over the local REST API, does not modify it, and copies none of its code. The REST client validates the fields it reads and accepts any other field, because the answers are another program's output.

## Alternatives considered

- **Linking the devices by hand in the Syncthing web interfaces.** Kept as the emergency fallback of the demonstration (the section on manual linking in the [stand README](../../../../docker/stand/README.md)), rejected as the way to link: each of two people on two computers pastes the other's device ID and replaces the device's default `dynamic` address with the relay address, because with discovery off `dynamic` finds nothing, and repeats it whenever a volume is recreated.
- **Syncthing's global and local discovery and the public relay pool.** Rejected: global announcements publish the device ID and addresses to discovery servers the team does not run, the public relay pool carries Syncthing traffic through nodes the team does not control, and local discovery finds nothing across networks; the demonstration must not depend on public nodes.
- **Syncthing's introducer and `autoAcceptFolders`.** Rejected: they let a device add folders or devices to the other Syncthing by Syncthing's own rules. Sharing the folder follows the trust the invitation established, so Ketos creates the folder on both sides itself and writes each peer device with `autoAcceptFolders: false`.
- **Ketos writing Syncthing's options itself.** Rejected: the options would have two writers. The bootstrap edits the file before Syncthing ever runs, so no moment exists in which Syncthing listens with the stock public settings; a runtime write would come after Syncthing had started with whatever the file held, and would overwrite an operator's change instead of reporting it.
- **Putting the relay token into `syncthing.relayAddress`.** Rejected: the token is the listening side's credential. It would sit in the plugin configuration and in every peer device's address list in the Syncthing interface, although dialing a peer never needs it.
- **Reporting `synced` from Syncthing's connection state alone.** Rejected: after a silent link loss the folder would stay `synced` for more than a minute next to a peer the board already shows as not connected. The Ketos channel, which has the heartbeat, is the faster witness, so `synced` also requires it.
- **Leaving a dead Syncthing connection to Syncthing's own timeouts.** Rejected: after the live 120 s cut, the folder showed `synced` for about 84 s while files did not move, next to a channel that was already online again.
- **Restarting Syncthing's connection at every channel reconnection.** Rejected after a live run: two reconnections within about two minutes used up Syncthing's forced redials, which then held off for five minutes while its relay redial waited for `relayReconnectIntervalM`, and the folder stayed waiting with no files moving for 211–350 s. The restarts also dropped Syncthing connections that had survived cuts of 20–65 s.
- **Reporting `syncing` from Syncthing alone while the channel is lost.** Rejected for the same reason as `synced`: the dead connection keeps Syncthing's view stale, so only `unavailable` and `error`, which do not depend on the peer, take priority over the channel.
- **Reporting `synced` from the local folder alone.** Rejected: when the peer added this device but its own folder step failed or still retried, the local folder is idle and needs nothing, and the state would read `synced` while the peer receives nothing. `synced` therefore also requires the peer's `remoteState` `valid` and nothing needed.
- **Refusing the plugin when the key is not set.** Rejected for this one case: the Syncthing feature is an add-on to a channel that already carries board synchronization and transcripts, and a missing key is reported by one log line and the absent `sharedFolder` field.
- **Embedding Syncthing or copying its code.** Rejected: copied files would fall under the MPL-2.0 obligations of Syncthing's files and make Ketos responsible for upstream fixes. A separate, checksum-pinned program is replaced by raising the pinned archive.

## Consequences

Two Ketoses link their Syncthings after one invitation: nobody opens a Syncthing interface, the exchange repeats at every reconnection as a read-only check, and a recreated Syncthing volume is picked up at the next reconnection. The shared folder trusts exactly what the channel trusts: a known peer's device ID is applied as sent, so a paired Ketos can add any Syncthing device of its choice to the shared folder. Per-person rights, worktrees, and a "remote access only" mode arrive after the demonstration, as does a password for the Syncthing interface, which listens inside the container without one and is published by the stand on `127.0.0.1` only. The interface keeps the unredacted relay token in its in-memory log and in the listen-address options, so whoever reaches it reads the token; the redaction of the log file does not cover it.

Outages of at least `kickAfterLostMs` are handled by restarting Syncthing's connection to the peer device when the Ketos channel connects again. A Syncthing relay connection that dies while the channel stays up, or during a shorter outage, stays counted as connected until Syncthing notices the loss itself: it sends a protocol ping at most every 90 s and closes a connection that has received nothing for 300 s, a check it runs every 150 s, unless the relay or TCP connection fails earlier. Only after that close does Syncthing redial the device through the relay, at most once a minute on the stand (`relayReconnectIntervalM=1`). Because every application resumes a paused peer device, a `ketos:<peer id>` device paused in the Syncthing interface is resumed at the peer's next channel connection; forgetting the peer is the way to stop syncing with it.

One folder only: the section names one `folderId`, and every linked peer device joins it. Peer devices are dialed only at the private Syncthing relay, a different program on the VPS from the iroh relay, so when it is down no new Syncthing connection between the computers is established while the channel and board synchronization continue.

Diverging Syncthing settings show as `error` but do not stop the linking. A step that Syncthing refused, for example for a wrong API key, does not retry: after the key is fixed the state recovers at the next poll, and the devices link at the next channel connection. A device renamed in the Syncthing interface is not found as the peer's previous device when the peer's ID changes, nor removed when the peer is forgotten, and the folder never reaches `synced`, because that state needs a connected device named `ketos:<peer id>`. A Ketos that returns with a new identity after all of its volumes were wiped is a new peer, so the device of its previous identity stays in the folder until that previous peer is forgotten. `synced` reflects the indexes this Syncthing has received: right after a connection, before the peer's index arrives, a side that has nothing to send can show `synced` for a moment although the peer holds files it has not announced yet. The REST client relies on the semantics of the pinned Syncthing 2.1.5, namely that a PUT resets omitted fields, that a PATCH replaces `devices` whole, and how a folder is normalized; raising the pinned version means checking them again against the stand-in described below.

## Testing

The `syncthing-*.spec.ts` files in `packages/ketos/peer/tests` cover the device ID check, the section checks and the settings comparison, the REST client, the linking, the shared-folder state, and the feature start with its key lookup, at 100% coverage per file. They run against `syncthing-fake.ts`, an in-memory stand-in of the Syncthing 2.1.5 REST API with the API key check, 404 for a missing folder or device, a PUT that builds from defaults, a PATCH that replaces `devices` whole, and folder normalization. The linking specs pin zero mutating requests for a repeated frame, rewriting only a device whose stored fields drifted, one folder PATCH when a frame and a connection arrive together with no device lost, the replacement of a device after an ID change, the removal of a forgotten peer's device from the folder and then the configuration, the pause and resume of an unchanged device after a channel loss of at least `kickAfterLostMs` and their absence after shorter losses, at a first connection, at a first linking, after an ID change, and for a repeated frame, the resume after a failed pause, the retry of a failed resume, the single resume without a restart of an identical device left paused, retry versus stop per failure class, and the absence of the key and the relay token from log lines and errors; the device ID spec refuses the 15 spellings with set padding bits that decode to the same bytes as each real ID. `syncthing-pair.spec.ts` runs two real peer nodes over the in-memory transport, each beside its own stand-in, and covers linking over the channel, the read-only re-check at a reconnection after a short loss, one pause and resume on each side after a 95 s loss, the replacement after a wiped volume, linking after a late-starting Syncthing, the removal of a forgotten peer's device, the `sharedFolder` field from `waiting` to `synced`, `waiting` while the peer's Syncthing has not set up the folder, and `waiting` while the Ketos channel is lost although Syncthing still reports the peer connected; `syncthing-state.spec.ts` pins that `syncing` and `synced` turn `waiting` and back between polls, that `unavailable` and `error` keep priority over the channel, and maps each remote state and need of the peer's device. `docker/stand/tools/syncthing-bootstrap.test.mjs` covers the first run, an unchanged rerun, a changed relay that replaces the old listen addresses, and the failures on template drift and a missing relay; `docker/stand/tools/stand-patch.test.mjs` covers the removal of the token from the relay address, and `run-with-redacted-log.test.mjs` and `docker-entrypoint.test.mjs` cover the log redaction and the Syncthing start. On the two-container stand with the relay-only overlay, both Syncthings were linked 0.8 s after the invitation was accepted, a file written by the model on one Ketos reached the other in 2.3 s, both channels were online again 4.6 s after one container restarted without a new invitation, and a wiped Syncthing volume was replaced and linked 3.5 s after its container came up.
