# Agent Note: An autonomous clone task is a goal over a live session, stored in `clone_tasks` and reported through one per-agent tool

Status: implemented

English | [中文](2026-09-23-ketos-stage-19-clone-autonomous-tasks.zh.md)

## Problem

After stage 18 a clone had a profile, memory, methodology, and skills, but it could only work when a person typed in its window. Stage 19 had to let a person state an objective and have the clone pursue it across turns without further prompting, keep a truthful status for every task, let the person read the result, and let them cancel — without writing an autonomy runner, without a second database, without a schedule or a cross-process queue, and without the browser holding the work alive: the plan's context states the harness already ships `ctx.goals.create(agent, { objective, maxGoalRounds })` plus the mounted `goal-round-driver`, which adds the next round whenever the agent returns to idle. The remaining questions were where a task's durable state lives, how a task ends, how a restart is reconciled, and how the browser learns about it.

## Decision

**A task is a row in `clone_tasks` in the same `clones.db`, added by forward-only schema step v5.** `id`, `clone_id`, `session_id` (null until started), `objective`, `status`, `result_summary`, `max_rounds`, `created_at`, `updated_at`, with an index on `clone_id` and one on `session_id`; `CLONE_CORE_SCHEMA_VERSION` becomes 5. A second database would duplicate the open sequence, the identity stamps, and the lifecycle ownership that `CloneDatabase` already owns, and a task is clone data exactly as a memory is. The status machine is `pending → running → done | failed | cancelled`, every transition is guarded by the status read inside the write transaction, and a terminal status is never rewritten; a repeated cancel is a no-op, while a repeated start is refused.

**The round budget is one validated config field, not a constant and not a wire field.** `defaultMaxRounds` defaults to 10 and is bounded to 50 in the schemastery schema; the cap is a validation invariant of the package, not a deployment setting, because a runaway task must not keep a session busy for an unbounded number of rounds. `create` stores the configured budget on the task and `start` hands exactly that value to the goal; the route deliberately accepts no per-request budget, because no current surface offers one. The generated `docs/config-catalog.md` carries the field.

**Autonomy is the shipped goal stack; clone-core owns only the seams.** `POST /api/ketos.tasks { op: 'start' }` runs on the host: the client creates the session through the ordinary remote `session.create` and passes its id, so the task's work never depends on a window staying open. The runner then binds the session to the clone (role `main`), awaits the clone-session coordinator's reconciliation so `clone_task_report` and the `clone:task` context are installed before the first round can enter the inbox, and calls `ctx.goals.create(agent, { objective, maxGoalRounds })`. The shipped `goal-round-driver` adds every later round on idle. A start is refused before any write when the task is not `pending`, the clone is not `ready`, the session has no live agent (`ketos/agent-not-live`), or the session already carries an unfinished goal; a failure after the status write releases the task back to `pending` and clears `session_id`.

**`clone_task_report` is a per-agent tool that files the report and completes the goal.** It is registered only in the scope of a session that currently runs a task — the coordinator reinstalls the scope when a task starts, and withdraws it when the task reaches a terminal status, deferring that withdrawal to the end of the turn when the terminal event lands mid-turn so the tool the model is still using does not vanish under it — and its absence is the ordinary clone session. The tool stores the summary while the task still runs and calls `ctx.goals.complete(agent, ref)`; without the completion the driver would keep adding rounds to `round-limit`. A terminal status follows from the durable goal and session events, never from a second timer: `goal/changed` with phase `complete` settles `done` with the stored report or the newest assistant text seen on the session event stream, phase `blocked` settles `failed` with the driver's message unless the block code is `cancelled`, and `session/disposed` settles a running task `failed`. Every terminal write tolerates a status that already moved, so a repeated event is harmless.

**Cancel blocks the goal durably and aborts the live turn.** `cancel` calls `ctx.goals.block(agent, ref, { code: 'cancelled', message: 'Cancelled by user' })`, which writes a `goal/change` record the log replays, then cancels the in-flight turn; the stored status becomes `cancelled`. The stage deliberately avoids `disarm` (process-local, no durable record, leaves `phase: 'active'` in the projection, desynchronizing the database) and `clear` (leaves a tombstone in the log); the plan names both exclusions.

**A restart settles interrupted tasks instead of pretending to resume.** The goal driver re-arms nothing after a restart and the interrupted round is gone, so the first open of the task table in a process settles every `running` task as `failed` with `the process restarted before the task finished`. That reconciliation lives in `CloneDatabase.openTaskRepository`, so the lazy open is preserved — a process that never touches tasks never imports `node:sqlite` — and any read or write through the task repository already sees the reconciled state. Automatic continuation is post-MVP.

**The goal service is read with `ctx.get('goals')`, not added to the plugin's root `inject`.** Clone, memory, and interview features do not need goals; making the whole package wait on that service would leave a deployment without goals serving no clone feature at all. The task operations fail loudly with a named error when the service is absent, and the shipped web profile always mounts it. This follows the documented rule that an optional service is read through `ctx.get`, and it keeps the deferred review of the root injection surface (`ketos-aqp`) from growing.

**The tasks window is a body of the existing board window kind.** The `'tasks'` `WindowKind`/`bodyKind`, its template, frame registration, title key, and layout allowlists already existed as a stage-5/7.2 stub, so 19.4 registers the missing `board.window.body` occupant instead of a new window or panel. The window lists tasks (all, or the window's clone), starts pending ones on a fresh session, cancels, opens the task's session through the existing `openChat`, and expands a row into the Markdown report plus the file artifacts folded from the chat snapshot the client already holds. While any task is `pending` or `running` the window re-reads the list every 750 ms — a named client constant, because a poll interval is not deployment-varying — and the interval stops with the last active task and on unmount; the browser still holds no subscriptions, and forwarding `goal/changed` to it is post-MVP. The Autopilot control on the clone card creates the task and starts it, then brings forward (or opens) the tasks window scoped to that clone.

**Round progress is read, not stored.** The window asks `ctx.remote.goals.get(sessionId)` for each running task and shows `roundsStarted / maxGoalRounds`; the goal projection is the authority and the task table stores no counter that a restart could falsify.

## Alternatives considered

- **A clone-core round loop (`agent/status` → `agent.followup`).** Rejected: it reimplements the shipped driver, including its reservation fence, checkpoint flush, and cancellation fencing, and the plan forbids changing the loop when an extension point exists.
- **A separate `tasks.db`.** Rejected: duplicate open sequence, identity stamps, and lifecycle ownership for data that belongs to a clone.
- **Adding `goals` to the root `inject`.** Rejected: it couples every clone feature to a service only autonomous tasks need, and it grows the injection surface the stage-18 audit already flagged.
- **Re-arming goals at process start (resume on restart).** Rejected for MVP: the plan puts automatic continuation post-MVP, and a resumed round would run against a workspace the interrupted round was mid-way through; the accepted behavior is a truthful `failed` and a new task.
- **Forwarding `goal/changed` to the browser instead of polling.** Deferred: it needs a remote-events allowlist change and a browser-side subscription path; the plan fixes the poll and the ≤ 1 s status SLA.
- **Storing a turns/rounds counter on the task row.** Rejected: the goal projection already carries `roundsStarted`, and a second counter would drift after a restart.
- **`disarm` or `clear` for cancellation.** Rejected: `disarm` leaves no durable record and keeps the projection `active`, and `clear` leaves a tombstone; the plan names both.
- **Making `clone_task_report` a global tool.** Rejected: the clone scope discipline registers every clone tool into the agent's own scope; a global tool would appear in ordinary chats.
- **A new `WindowKind`, a tasks panel, or a clone-window tab for tasks.** Rejected: the `'tasks'` window kind was reserved for exactly this stage, and the clone window already carries three tabs (profile, interview, memory) whose scope is the clone record, not its work.
- **A per-request `maxRounds` wire field.** Rejected: no current surface offers a budget, and the plan makes the value a config field with a fixed validation cap.

## Consequences

A person can now state an objective on a clone card or in the tasks window and let the clone work: the host creates the goal, the shipped driver adds rounds, the clone files its report with one tool, and the window shows the status, the report, and the artifacts without a person prompting the session. The costs accepted: a running task does not survive a restart and continuation is a new task; cancel is terminal, so re-running means a new task; the window polls rather than receiving pushed events, and round progress is best-effort; the report is exactly the text the clone filed, and the artifact list only covers sessions this client already holds. The database moves to `user_version = 5`; the step is forward-only, and a version 4 file is adopted by running v5 alone. The MVP coverage policy is unchanged: `packages/ketos/clone-*/src/**` and `packages/client/ui-board/src/**` stay outside the per-file gate with behavior suites instead.
