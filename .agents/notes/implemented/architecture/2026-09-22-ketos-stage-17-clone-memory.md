# Agent Note: Clone memory is one FTS5 store in clones.db, composed into the clone session scope and edited in the clone window

Status: implemented

English | [中文](2026-09-22-ketos-stage-17-clone-memory.zh.md)

## Problem

After stage 16 a clone could be interviewed and hold a profile, but every session with it started blank: nothing the clone learned or was told survived the session, and the profile itself never reached the model. The stage had to give a clone long-term memory — save, search, and inject it — without a second database to keep consistent, without a semantic-search dependency, without rewriting the request prefix on every remembered fact, and without letting an ordinary chat see another session's knowledge. The memory also had to be visible and editable by the person, because a clone that remembers something wrong must be correctable without deleting the clone. Harness has no memory subsystem; its session search is a disposable derived read model, not a store.

## Decision

**Memory lives in the same `clones.db`, as a step of the same forward-only runner, with a standalone FTS5 index kept by the repository.** Schema step `v3` adds `memories` (id, clone_id, content, tags, source_session_id, status, created_at, updated_at), an index on `(clone_id, status)`, and `memories_fts` — a standalone FTS5 table (`id UNINDEXED, content, tags, clone_id UNINDEXED`, `tokenize='unicode61'`), the same shape `session-query-sqlite` already ships. The alternative of a second file would have made clone deletion, backup, and file identity two problems instead of one; the alternative of an external-content table with triggers was rejected because a trigger is a hidden synchronization point this package cannot test, while repository-side synchronization inside the write's own transaction is explicit and testable. Every table write (`remember`, `updateMemory`, `deleteMemory`, and `deleteClone`) deletes the index row by `id` and inserts the new one in the same immediate transaction, so only a hand-edited database can desynchronize them; `deleteClone` removes a clone's memory with its bindings, so no memory outlives its clone. A memory carries a `status` — `active`, `candidate`, `archived` — and the clone-delete path is the only cascade.

**Search is quoted token prefixes, and it is the same expression for both surfaces.** A query is split on whitespace, every token that holds a letter or digit becomes one quoted FTS5 phrase with a trailing `*` (`"навык"*`), and tokens are joined with FTS5's implicit AND. Quoting keeps query syntax inert data — a query of `"`, `OR`, or `"незакрытая` is either refused as tokenless or matched literally, never parsed as syntax — and the prefix marker finds inflected Russian forms even though `unicode61` does no stemming, which the plan required without adding a stemmer or an embedding model. `search` returns non-`archived` rows by default and one exact status when asked; `listMemories` returns every status or one. The plan's 20 ms budget for ten thousand records holds with the index and rank ordering the repository builds: the benchmark measures a selective keyword query by wall-clock median and the worst case — a term every stored record holds, so BM25 ranks all ten thousand — by CPU time, which a forked spec worker's descheduling cannot inflate.

**The per-agent interview scope becomes the clone session scope: one scope per bound agent, carrying the profile, the memory, and the interview.** `src/interview.ts` was renamed to `src/session.ts` and `CloneInterviewCoordinator` to `CloneSessionCoordinator`, because the coordinator now reconciles on any binding rather than only an interview. One `agent.ctx.inject(['tools', 'systemPrompt'], …)` scope registers, for every session bound to an existing clone: the `clone:profile` section built from the stored record (name, role, summary, persona, methodology, skills — never a secret the person did not author), the `clone:memory` prompt context, and the `clone_memory_remember` and `clone_memory_search` tools; when the binding role is `interview` and the clone is `interviewing` it additionally registers the stage-16 interview section, `clone_draft_save`, and the exactly-once kickoff. The stage-16 reconciliation machinery — lifecycle triggers, the per-agent chain, the batch, the kickoff latch, disposal re-checks — is unchanged, so the shipped order that writes the binding after the agent exists still works and no ordinary session ever sees any of it. The scope is reinstalled when the clone identity or the interview mode changes, and refreshed in place otherwise: the prompt providers close over a mutable text holder that reconciliation replaces, so a profile edit or a memory write republishes the new text without re-registering tools or sections.

**The profile is a section and the memory is a context, which is what keeps the KV cache.** The profile rides `systemPrompt.section` because it is the clone's stable identity: its text changes only when the person edits the record, so the request prefix is byte-identical between turns while the agent works. The memory rides `systemPrompt.context` because it changes whenever the clone learns something: it materializes as a durable runtime-context user message on the next turn, so a new memory never rewrites the stable prefix, and a memory change costs a suffix message instead of a cache miss. Both surfaces read the same stored rows, so the person's window and the agent's next turn cannot disagree; a write from either path re-derives the snapshot through the same route notification the interview already used. The snapshot lists the newest `memoryEntries` active memories (default 10) rendered into at most `memoryChars` characters (default 8000, about 2000 tokens), shortening one over-long memory and counting the ones the budget dropped, with the search tool as the deeper lookup; both numbers are validated `Config` fields because a deployment's context budget varies.

**The memory tools are the clone's, and they re-check the binding where they execute.** `clone_memory_remember` (content at most 4000 characters, optional tags and a `methodology_candidate` flag that stores `status='candidate'`) and `clone_memory_search` (limit at most 20, `isConcurrencySafe` because it only reads) are registered into the agent scope, never globally. Both resolve the clone from `exec.agent.id`'s own binding at execution time — not from the scope's installation — so a tool call that outlives the binding is refused with `ketos/not-a-clone-session` instead of writing into a clone the session no longer owns, and the repository refuses the bounds as `ketos/invalid-memory` because a tool schema can express neither `maxLength` nor `maxItems`. `remember` stays exclusive like the other clone write tool; `search` opts into parallel scheduling.

**The memory window is a third tab of the clone window, and the person's edits flow through `/api/ketos.memory`.** The plan left the format open between a window and a tab; the tab won because the clone window already owns the frame, the `cloneId`, the session bridge, and the layout entry, so a memory window would have added a `WindowKind`, a frame registration, a panel registration, a title key, and a dock glyph for no new capability. The route is the second exact Fetch route: `list`, `search`, `update`, and `delete`, all scoped by `clone_id`, with `ketos/invalid` and `ketos/memory-not-found`; it validates the same bounds the repository does and notifies the coordinator after every accepted write, which is how a deletion in the window disappears from the agent's next assembly. The window body lists the selected status, searches, edits content, tags, and status inline, and deletes behind one confirmation; it re-reads the list after every mutation instead of keeping a local model, so the rows always show what the store holds. A read the route refuses renders its own failure row — a retry for a broken store, a refused-search notice when the route rejected the query — rather than an empty memory, and a tag must be one line without the editor's comma because that form could never round-trip through it.

## Alternatives considered

- **A separate `memories.db` file.** Rejected: the clone domain already owns a file, an identity stamp, a migration runner, and a lazy handle; a second file doubles that surface and makes deleting a clone a cross-file transaction with no atomicity.
- **An FTS5 external-content table with triggers.** Rejected: triggers move synchronization out of the repository into DDL the package cannot unit-test, and a hand edit desynchronizes the index silently; the repository's explicit delete-and-insert inside the write transaction is the pattern `session-query-sqlite` already ships and this package can assert.
- **A hidden `rowid` join instead of explicit `UNINDEXED` columns.** Rejected: the plan pins the canonical shape — explicit id and clone columns — so the index can be joined, filtered, and cleaned up by the same columns the table uses.
- **Semantic search with embeddings (`sqlite-vec` or cosine in process).** Deferred: the spike is not available in the MVP, and lexical prefix matching covers the stage's acceptance criteria without a second store or a background indexer.
- **Injecting memory as a prompt section.** Rejected: a section that changes whenever the clone remembers something would rewrite the request prefix and drop the KV cache on every fact; the runtime-context message is the mechanism that exists for exactly this.
- **Injecting the whole memory into the prompt.** Rejected: unbounded growth and no ranking; the budgeted newest-N snapshot plus a search tool keeps the context cost predictable and lets the model ask for the rest.
- **Storing memories as clone record fields or a session projection.** Rejected: memory is many rows per clone with its own search, and a session projection is a derived read model that dies with the session; the store must outlive every session.
- **Revision-checked memory edits.** Rejected: a memory has one author at a time and no editing form that holds a snapshot for long; last-writer-wins with an immediate re-read is honest, and the window never shows a row the store does not hold.
- **A dedicated memory window kind.** Rejected: it duplicates the clone window's frame, session, and layout surfaces; the tab reuses all of them and keeps one window per clone record.
- **A memory summary in the chats panel.** Rejected: the plan allowed either surface, and a read-only summary beside projects would add a second rendering of the same rows without an editing path; the tab is the one memory surface.
- **Per-clone memory budgets in the clone record.** Rejected: the budget is a deployment context decision, not a clone property; the `Config` fields follow the existing `maxResults`/`maxEntries` pattern.

## Consequences

A clone now remembers: the agent saves facts with a tool, finds them with a search, carries the newest ones into every request as runtime context, and the person can list, search, edit, archive, or delete them in the clone window, with each change reaching the agent's next turn. The stage-16 scope grew from an interview-only mode into the clone session scope without changing its lifecycle machinery, so the interview still behaves exactly as it did. The costs accepted: every stored clone change or memory write re-derives the scope of every live top-level agent (a database read per event, not a cache); memory search is lexical, so a query only matches tokens that literally share a prefix; `candidate` is a status the window shows, with no quarantine pipeline behind it; a memory edit is last-writer-wins rather than revision-checked; `archived` rows stay in the file and leave only the agent's two surfaces; and the memory window re-reads the complete list on every mutation instead of paginating, which is honest for a local single-person store but will need paging if a clone ever holds thousands of memories.
