# Agent Note: Clone methodology is four canonical sections, and clone skills are record objects registered into the agent's own skill-registry layer

Status: implemented

English | [中文](2026-09-22-ketos-stage-18-clone-methodology-skills.zh.md)

## Problem

After stage 17 a clone carried a persona, a free-form methodology paragraph, and memory, but nothing it authored was structured or callable: the methodology was one blob with no signal that a section was missing, the record's `skills` was a list of bare names with no description or instructions, and no part of the harness consumed it — the model never learned which skills the clone had and could not invoke one. The stage had to make the methodology structured, make skills authored and callable units, and keep both manageable by the person from the clone window, without generating a preset per clone, without skill files, without a second database, and without letting an ordinary chat see another clone's skills. The harness already has the mechanism: the skill registry (`ctx.skills`) layers per scope, and an Agent is its own scope key, so a runtime registration into `agent.ctx` is visible to exactly that agent.

## Decision

**The methodology vocabulary lives in `packages/ketos/clone-core/src/methodology.ts` and is browser-safe.** `METHODOLOGY_SECTIONS` names the four canonical level-two headings — `Принципы`, `Порядок работы`, `Критерии качества`, `Чего не делать`; `METHODOLOGY_TEMPLATE` is the same four headings with blank bodies; `methodologySections(text)` reports each heading as present and/or empty and `methodologyGaps(text)` collects the missing-or-empty ones. The parser reads level-two headings only, so a level-three heading or a lookalike title is not a section. The module imports nothing and holds no state, so the editor runtime-imports it and the client bundle inlines it (the package exports `./methodology`, and `tsconfig.base.json` maps the specifier); the host keeps the vocabulary, the browser half reads it.

**The interview writes the structure and the editor shows the gaps, softly.** The interviewer instruction lists the four `## <heading>` sections and asks for concrete content under each, and for every skill a kebab-case name, a short description, and instructions. The editor parses the live draft and marks each section `filled`, `empty`, or `missing`, shows a gaps hint, and offers a template insert while the field is blank. Validation stays soft by design: a gap is a warning, never a reason to refuse a save, because a profile in progress is expected to have holes. The profile section injects the stored methodology markdown unchanged.

**A clone skill is `{ name, description, instructions }`, stored as objects in `skills_json`.** Schema step v4 rewrites a legacy array of names into objects with empty description and instructions, preserving order, and leaves object arrays untouched. The durable decode guard enforces the object shape only — not the name grammar, not uniqueness — so a database written before the grammar was enforced stays readable; the route and `clone_draft_save` are the write boundaries that enforce the grammar (`^[a-z0-9]+(?:-[a-z0-9]+)*$`, at most 64 characters, unique within the clone), the field bounds (description at most 500, instructions at most 20000, at most 100 skills), and refuse violations with `ketos/invalid` and `ketos/invalid-draft`. Empty description and instructions are legal draft state: the editor flags an undescribed skill instead of blocking the form.

**`clone_draft_save` merges skills by name instead of replacing them.** A stored skill the interview does not mention keeps its place, a same-name one is replaced in place, and a new name appends in draft order. The person can add a skill while an interview runs without the next draft save dropping it; the tool description states the merge so the model is not told omission deletes.

**Registration is one more scope inside the agent, never a preset or a file.** For an agent bound to a clone, clone-core registers every registerable skill — its name matches the registry grammar, stays within the length bound the write paths enforce, and its description is non-empty — through a separate `agent.ctx.inject(['skills'], …)` with `source: 'runtime'` and the registry's default invocation policy (`modelInvocable` and `userInvocable`). The separate inject is deliberate: a deployment without a skill registry leaves the skills fiber pending while the profile section, the memory tools, and the interview mode install exactly as before. Registrations belong to the agent's scope and die with it; a registration failure is a logged warning, not an unhandled rejection. The model meets the skills through the catalog `tool-skill` publishes at each step, with each description, and loads one with the `skill` tool; the `clone:profile` section deliberately names no skills, because the registered set of a live scope cannot change and a profile line would advertise skills that live agent cannot load.

**Editing a clone reaches a live agent's skills only on recreation, which the stage accepts and records.** Reconciliation reinstalls the scope for a different clone or a different interview mode and otherwise refreshes the profile and memory text in place, so a person's methodology edit reaches the running session on its next assembly while a skills edit waits for the scope to be reinstalled or the agent to be recreated. Pinning sessions to a clone revision is out of MVP scope; the record's `revision` and `updatedAt` are surfaced in the editor so a person can see a save landed.

**The editor stays a body of the clone window.** The methodology field gained the live structure strip, the gaps hint, and the blank-only template action; the new Skills section lists the draft's skills with an incomplete-skill warning, adds and edits through a modal (grammar, uniqueness, count, and length validation), deletes through the row menu the chats panel already uses, and marks stored names the host will refuse or leave unregistered. No new window kind, wrapper component, or document was introduced.

## Alternatives considered

- **Generating one agent preset per clone.** Rejected: the preset roster is deployment configuration, and the plan's stage context already establishes that registering into the agent's own scope omits preset generation entirely.
- **Skill files under a per-clone directory (`customSkillDirs`).** Rejected: a clone's skills are record data, and files beside the record would need their own lifecycle, cleanup on rename and delete, and a second source of truth for the editor.
- **Keeping `skills` as names and adding a lookup tool.** Rejected: a name alone cannot route the model (the catalog needs a description) and cannot instruct it (the body needs instructions), so the record would still lack the authored fields.
- **Enforcing the kebab grammar in the durable decode.** Rejected: a pre-stage database could hold any name, and a throw at decode makes the whole clone list unreadable; the editor flags the name and registration skips it instead.
- **Requiring a non-empty description at write time.** Rejected: a person may name a skill before describing it, and blocking the form for an incomplete draft is worse than the visible warning and the skipped registration.
- **Re-registering skills on every clone data change.** Rejected: the stage fixed the accepted simplification that a live scope keeps its registered set; the profile and memory text still refresh, and recreation applies the new list.
- **Listing skill names in the profile section.** Rejected: it duplicates the catalog and goes stale the moment a live scope keeps its old registered set, telling the model about a skill the `skill` tool would refuse to load.
- **Four separate textareas, one per methodology section, instead of one markdown field.** Rejected: the record is markdown, unknown sections must survive a round trip, and one editing surface plus a parsed structure strip keeps the store format and the review aid separate.

## Consequences

A clone's methodology now has a canonical shape the interviewer fills and the editor audits, and a clone's skills are authored units the model sees in its catalog and invokes with the `skill` tool in the clone's own sessions; the person adds, edits, and deletes them in the clone window, and the record's revision and update time show what a save did. The costs accepted: a live session keeps the skills it registered at installation until it is recreated, skills are not revisioned with the record, an undescribed or legacy-named skill stays out of the model's catalog until the editor fixes it, and the methodology's four sections are a convention the editor warns about rather than a validation the store enforces. Schema version 4 is forward-only; a database written by this build is refused by earlier ones, and a legacy name array is preserved as object-shaped drafts.
