# Agent Note：导航外壳——dock 状态、Omnibox 投递与检查器芯片

Status: implemented

[English](2026-09-18-ketos-navigation-shell.md) | 中文

## 问题

阶段 6 完成了聊天窗口，但它周围的四个面仍然是桩。dock 按名字列出窗口并把视图居中，却对它们的会话一无所知：正在创建、正在执行或已损坏的窗口与普通行看起来完全一样，而关闭窗口的唯一方式是外框上的按钮。Omnibox 根本没有接上会话——Enter 只清空输入框，附件、听写与网页搜索条目只是悄悄关闭菜单——而且没有任何看板面能打开工具窗口，尽管 `WindowFrame` 自阶段 4 起就服务全部六种类型。元素选择浮层能画出选框与胶囊，但点击没有任何效果：既没有捕获格式，也没有通往窗口草稿的路径。层一致性还留有两个尾巴：聊天面板的 overlay 呈现位于画布变换内部，其层叠上下文把它限制在根级浮层之下，因此 Omnibox 可能压住面板下缘（`ketos-0iy`）；而看板浮层各自计算自己的方向与对齐。

## 决定

**dock 读取与外框相同的窗口 channel，并且各行直接作用于 store。** 每一行通过 `windowTitle` 解析标题，并从外框已经在用的 keyed `useWindowSession(windowId)` 席位读取状态，因此一个 channel 同时服务两个面，也没有任何组件自行订阅。状态就是 channel 拥有的会话事实：会话缺失或待创建读作创建中；创建、提示词或回合失败先于运行中的回合读作错误；运行中的回合读作执行中；其余就绪会话读作空闲。`StateDot` 渲染它，`rail.statusLabel` 把本地化状态与标题并列作为无障碍名称。点击当前窗口的行只聚焦它——视图已经居中于它——而点击其他行会居中并聚焦。行的右键菜单（`onContextMenu`，共享的经 portal 渲染的 `Menu`）通过既有的就地编辑器重命名，或关闭窗口；关闭条目会说明聊天仍留在列表中，因为事实如此：窗口离开 store，窗口层释放桥记录，而会话保持存活。dock 的 `+` 保留一键添加 agent；其右键菜单打开与 Omnibox 相同的类型目录，因此两个浮层都能创建阶段 7 拥有的窗口类型。

**所有看板浮层命令共用同一条寻址规则。** `open-window.ts` 解析命令作用于哪个窗口：有当前聊天窗口时用它，否则按模板尺寸新建一个 agent 窗口。Omnibox 的发送与检查器的芯片都经过它，因此两个面都不会发明自己的回退。投递经过窗口桥而不是私有的会话路径，并且桥现在会等待窗口的会话创建（`whenReady`）后再发送：Omnibox 可以在同一个手势里打开窗口并提交，此时新 composer 尚未挂载、会话尚未创建。会话创建期间被关闭的窗口保持关闭——桥在绑定前确认记录仍然存在。

**Omnibox 用真实动作或明确原因替换每一个桩。** Enter 去除草稿首尾空白，把它作为排队回合送进被寻址窗口的会话。`+` 菜单的「新建窗口」一节从 `BOARD_WINDOW_TEMPLATES` 打开 agent、连接器与设置窗口，并对克隆、仪表板与任务给出计划允许的本地化「暂不提供」提示，因为这些面属于后续阶段。附件把文件选择器命令经由 composer 意图队列路由；听写把 `useDictation` 切换进 Omnibox 草稿，并在浏览器不支持时给出提示；网页搜索说明 `web` 能力位于宿主侧、客户端没有路径，这是客户端诚实的边界，而不是缺失的接线；选择元素启用检查器。菜单经 portal 渲染，并与所有其他看板浮层共用同一条放置规则（`menu-placement.ts`），因此无论触发器在哪里，列表都开在空间更充裕的一侧。

**检查器捕获确定性描述，并通过 composer 插入纯文本芯片。** `element-capture.ts` 构造 `tag:nth-of-type(n)` 选择器（锚定在最近一次看板表面或 `body`），以及一段语言无关的稳定事实描述：标签、所在窗口的类型与标题、`data-board-action`、无障碍名称、工具提示，以及 60 字符的文本摘录。浮层的层已经让指针通过，因此捕获运行在捕获阶段的 click 监听器上：它豁免落在自身胶囊内的点击，遇到打开中的菜单时让位（与 Escape 相同的优先级），只认领看板表面之内的点击，使应用自身的外壳保持其含义，并抑制默认动作，使指针下的控件绝不会被激活。这次拾取变成一条由 `resolveChatWindow` 寻址的 `ComposerIntent`；被寻址的 composer 消费意图——文本追加到草稿，文件选择器命令在 composer 能接受文件时才点击文件输入框，窗口关闭会丢弃其排队命令，因此队列不会积累孤儿。composer 没有编辑器芯片（阶段 4 的限制），因此芯片就是草稿文本，用户可以像编辑其他提及一样编辑或删除它。

**展开的聊天面板让整个浮动浮层让位。** `ketos-0iy` 通过一致性而非搬移面板来解决：面板仍是画布变换中的一层，其几何、缩放与菜单行为已经成立；而根级浮层——dock、Omnibox 与小地图——在面板展开期间停止渲染，正如 dock 与小地图此前已经如此。再也没有留给根级浮层去覆盖的东西：面板外缘、缩放手柄，以及 overlay 呈现下窗口的下缘都可达，而全屏外框此前就已经以同样方式让浮层让位。`BoardViews.tsx` 与 README 中的层阶梯陈述了这条最终规则。

## 备选方案

- **像手柄环一样把聊天面板搬到根级、屏幕空间的层。** 否决：面板的宽高与排版将不再随画布缩放，其已有文档的世界单位几何与每一个面板几何测试都要重写，菜单还需要第二条放置路径——对一个 P3 重叠而言这是巨大的行为变更，而浮层让位无需触碰面板即可解决。面板保留其变换层与已被记录的跟随行为。
- **dock 每行一个可见的关闭按钮。** 否决：导轨是 38px 的图标列；第二个控件会让它旁边的状态字形变得拥挤，而行菜单在保持导轨紧凑的同时把重命名条目与关闭并列。关闭标签的提示告诉用户聊天仍会保留。
- **让 Omnibox 文本直接经过 `ctx.sessions` 发送。** 否决：那会重复队列/引导策略与窗口桥拥有的会话创建顺序；桥是同时服务 composer 的唯一路径，而它的 `whenReady` 等待正是「打开后立即发送」可靠的原因。
- **通过被寻址会话调用 `web_search` 工具。** 否决：菜单条目不携带查询词，而 `web` 服务是客户端插件无法注入的宿主能力；显式的本地化原因是计划允许的诚实结果，而隐藏的提示词会花掉用户并未请求的模型回合。
- **只捕获选择器。** 否决：模型能通过选择器定位节点，却无法判断它是什么；描述中的窗口类型、标题、动作 id 与文本摘录才让芯片可用，而每个部分都是稳定的 DOM 事实，而非本地化文案。
- **检查器捕获使用编辑器芯片。** 与阶段 4 拒绝 `@` 提及使用编辑器芯片同理：看板 composer 是 textarea，而不是对话包的编辑器；芯片组件需要一个该包并未定义的编辑器槽位。

## 后果

看板浮层现在如实报告每个窗口，而 Omnibox 此前是桩的三个条目要么执行、要么说明为何不能执行。检查器闭合了从画布到模型提示词的环路：被拾取的元素成为被寻址窗口聊天中可编辑的草稿文本。接受的代价：窗口状态仍是粗糙的四态投影，没有逐工具进度；芯片是草稿文本，而不是可移除的编辑器芯片；网页搜索与克隆、仪表板、任务窗口在本 MVP 中报告不可用；而聊天面板打开期间 Omnibox 不可达，因此想打开窗口或检查元素的用户需要先折叠面板（面板导轨让这一步只差一次点击）。`ketos-md8`（工具窗口模板）与 `ketos-0iy`（面板位于浮层之下）由本阶段关闭。看板仍然只注入阶段 6 的服务集合：`minimap.aria` 只需要既有小地图条目声明 `locale: NS`，没有任何新包、清单或生成目录发生变化。

验证：`tests/dock.client.spec.tsx`（状态投影、居中/聚焦点击规则、行菜单的重命名与关闭且会话仍留在列表中、添加目录、层规则）、`tests/omnibox.client.spec.tsx`（发送进当前窗口、没有可寻址窗口时新建、不可用提示、类型创建、附件意图、portal）、`tests/element-capture.client.spec.ts` 与 `tests/inspector.client.spec.tsx`（选择器与描述组合、捕获阶段点击及胶囊与菜单优先级、经由看板组合的芯片、无窗口回退）、`tests/composer.client.spec.tsx`（意图消费、等待中的文件选择器）、`tests/store.client.spec.ts`（意图队列、消费与随窗口关闭丢弃）、`tests/minimap-layers.client.spec.tsx` 与扩展后的 `tests/canvas.client.spec.tsx` Minimap 块（工具类型、二十个窗口、frustum 下限、拖动平移、重投影、层门控）、`tests/slots.client.spec.tsx`（完整的 Escape 阶梯，含菜单优先的一次按键、浮层让位与返回），以及实机审计 `.playwright-mcp/stage-07-gif/audit.mjs`（50 项检查，ru-RU 与 en-US 均 `ok: true`，其中包含针对 `ketos-0iy` 的 `73-panel-bottom-edge-hit`）。
