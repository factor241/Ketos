# @deepseek-ai/dsh-client-ui-board

English | [中文](README.zh.md)

## Summary

The board is a spatial main panel for the dsh web client: an infinite canvas of movable, resizable, stackable agent windows, each owning a Harness session and the chat composer. The lane renders every tool call as a card (terminal, read, diff, search, citations, to-dos, image, question transcript) with elapsed seconds, localized failure or stopped states, and a JSON fallback, and banners a pending approval before navigating to the main panel's answering composer. A dock lists windows, the Omnibox sends into the active chat, and a minimap mirrors the layout. It draws the `board` panel on the shared theme.

## Use this package

Open the board panel through the board icon in the sidebar panel list; the canvas fills the main panel and starts empty. Drag the background to pan, wheel to zoom (0.2–2.0, centered on the pointer), and use the dock's plus button to add an agent card at the center of the current view (a right-click on the plus opens the catalog menu for agent, connectors, and settings windows). Window interactions follow one convention: drag the header to move, drag an edge handle to resize one axis, drag a corner handle to scale the window proportionally (both axes by the same factor, the opposite corner anchored), and hold Shift while dragging to disable the 24 px grid snap; clicking a window brings it to the front of the z-order, and its close button removes it. A Space-drag or a middle-button drag pans from anywhere on the board — the floating chrome included, and a middle-button drag on a handle pans instead of resizing — and `Ctrl/Cmd+0` resets pan and zoom. A wheel over a window lane scrolls that lane while a wheel over the canvas or the floating chrome zooms toward the pointer. The active window's eight resize handles are also drawn above the floating chrome, so an edge that slid under the dock, omnibar, or minimap stays grabbable. The ring sits just outside the frame, so the header's controls stay clickable even when a zoomed-out canvas scales them below the strip's thickness. A window that leaves the visible canvas stops painting — its lane, draft, attachments, and chats panel stay live — and returns unchanged when the view comes back; the fullscreen window's neighbours stand down the same way. Escape performs one action per press in the order menu, focused editor, element selection, chats panel, fullscreen. A window never shrinks below the size it is created with (the default chat size, 552×648 for an agent window) — the composer's rows cannot lay out in less — while growing in width, height, or diagonally is unbounded. The window renders one scale above the app: its titles, lane text, chips, controls, and composer read one metric set (`--board-font-*` and the control, padding, and gap values) declared on the board root, so the frame and its contents grow together while the dock, omnibar, minimap, and portalled menus keep the app's sizes. The header's chats button opens a panel that slides out of the window's left edge (the right one when the left has no room): the window's control surface for projects and chats. The projects level lists every workspace that holds a visible chat plus an ungrouped bucket, and its header registers a folder (the browser lists one directory level with clickable crumbs and creates nested folders before registering the picked directory; a host that mounted the native chooser instead serves no listing, so the level then hands the pick to that chooser and registers what it returns), opens a search field, and opens the grouping and ordering menu (group by project or one list; manual order or last updated). Every row has a trailing menu — projects rename, move up or down, and delete (a registration only; chats and files stay), chats rename, branch at their last completed turn (the window then shows the child), move, and archive — and a drag on a row commits the same move. The chats level lists one project's chats with their relative age and a running marker; picking one points the window at it — or, when another window already shows that chat, brings that window forward and leaves this one alone — and its header creates a chat in that project (reusing the project's blank chat while no other window shows it). The panel is a layer of its own above the canvas: 300px wide by default, resizable by dragging its outer edge between 260 and 420px (never more than the room the frame leaves), at the frame's own height, following the window while it moves, resizes, pans, or zooms. Collapsed — and for every chat window that never opened it — a compact 44px rail at the same edge keeps the panel one click away, and the panel's own header carries the control that collapses it again. The board's whole floating chrome — the dock, the Omnibox, and the minimap — stands down while a panel is open and returns when it collapses to its rail, where it no longer covers anything, so no root-level layer covers the panel's outer edge, its resize handle, or the window's bottom edge in the overlay presentation. Escape closes the panel first and leaves fullscreen second. In fullscreen the panel docks along the board panel's left edge as the plain sidebar of a normal chat layout, with the chat centred on a 768px column beside it. Selecting a window in the dock or minimap focuses it and centers the view on it, except that the active window's dock row only focuses it. Every dock row resolves the window's title, its kind, and the status its session channel reports — Creating or Restoring while the session is absent, pending, or waiting for the session list, Running while a turn runs, Error on a creation, prompt, turn, or vanished-session failure, and Idle otherwise — and the row's localized accessible name pairs the title with that status; a right-click opens the row's portalled menu with Rename (an in-place editor) and Close window, which removes the window while its chat stays alive and listed. The header and the dock name the window with its chat's title, fall back to the kind's localized template until a chat has a title, and follow a chat rename or a rebind; clicking the header name — or double-clicking the dock row — edits a window name of the user's own, which overrides the chat title until it is cleared. The first time a window renders it creates its own session (the session appears in the sidebar list, and focusing the window makes it current); a window restored from the saved layout reattaches to the chat it was showing, and a chat the host no longer lists leaves the window in its missing state — the lane names it and offers New session and Choose a chat until the chat returns or another is picked. The Omnibox sends on Enter or Send: it trims its draft and the bridge delivers the text into the active chat window's session as a queued turn, opening an agent window when no chat window is addressed; the bridge waits for the session's creation, so delivery right after a window opens is not lost. Its `+` menu carries a New window section — agent, connectors, and settings open real board windows while clone, dashboard, and tasks answer with their localized unavailable-in-this-MVP notice — plus a recent-chats section listing the six most recently updated chats with their directories (reopening one follows the same bring-forward rule), and capability entries: Attach file routes a file-picker command into the addressed window's composer, Dictate toggles dictation into the Omnibox draft and reports when the browser cannot start it, Web search states that the host-side web capability has no client path in this MVP, and Select an element enables the inspector; every board menu is portalled and opens on the roomier side. Clicking an element while the inspector is active captures a deterministic `tag:nth-of-type(n)` selector path — anchored at the board surface, or at `body` — plus a language-neutral description of the element's tag, containing window kind and title, `data-board-action`, accessible name, tooltip, and a 60-character text excerpt, and appends the localized chip to the addressed window's composer draft under the same active-chat-window-else-new-agent-window rule the Omnibox uses; the overlay passes pointers through, claims the click in the capture phase so the control under it never activates, yields to an open menu, and Escape cancels. The composer mirrors the main chat: `+` opens the action menu (files and images, goal, plan, feedback, compact, permission, export), `/` filters the slash commands with their hints and descriptions, `@` suggests files, directories, and sessions with a localized kind, the chip row switches the permission preset (full access behind the risk confirmation) and the model with its reasoning effort, and the ring shows context occupancy, and the microphone button dictates into the draft through the browser's speech recognition where the engine exposes it; a line that leads with a known command executes against the session with its arguments — and with the draft's images and staged files, so a command that does not accept attachments is refused by the host with its own reason — while images obey the host's projected limits (a batch over the count, per-image size, or total is refused with the localized reason) and other files upload in the background and ship as receipts; the card also accepts files dropped onto it or pasted into the field; the agent-preset chip is the only setup chip in the composer (the working folder lives in the window's chats panel), and the panel's folder action registers a picked directory as a project folder for new chats; a new window starts with the board's remembered preset — the last preset picked in the chip or through the Omnibox's Preset entry becomes the default, is stored with the layout, and is applied to the window's fresh blank session — while a preset the host refuses renders its localized reason under the composer, a session that already started disables the chip with that reason in its hint, and a preset that cannot compose a session is never offered; the model chip's tooltip names the model and the reasoning effort in force and states that a switch is saved as the system default for new sessions, and a model-catalog failure renders inside the model menu while the window keeps working. Enter sends, Cmd/Ctrl+Enter steers the running turn, Shift+Enter inserts a newline, and the round button stops; every send registers a local echo in the lane before the host admission, and the draft and its chips return untouched exactly once when the host refuses the prompt (a composer the user has typed into keeps its newer text and gains the refused draft as a new paragraph); a queued message renders in the strip above the card with its attachments and offers edit (its text only), remove, and steer while a turn runs, queued echoes still awaiting their occurrence render as sending rows, a refused queue change shows the host's reason in the strip, and a cancel keeps the queued work the host resumes in order; steering corrections — pending and durable — render in the lane as their own user bubbles, and a durable turn failure renders as one localized card whose expandable detail carries the provider message and code and whose repeat action re-sends the failed turn's prompt, with the channel's generic failure line appearing only when no card carries that failure; the card measures itself and drops chip labels or wraps the tool row as the window narrows, so the send control stays reachable at every size; `Load earlier turns` pulls the previous turns into the lane with one compensating scroll write (native scroll anchoring is disabled so the adjustment cannot double), keeping the reader's position and disabling itself while a page is in flight; the lane renders every tool call as its card and keeps a running call's elapsed seconds visible while it executes, a call the card table cannot read falls back to a collapsed JSON block, a settled result whose call is outside the loaded window keeps its unavailable line with a repeat control, and the empty, creating, failure, running, and blocked states each render their own localized line; and the header's fullscreen button fills the board panel with the window until Escape or the same button brings it back; the other windows and the dock, omnibar, and minimap stand down while the window is fullscreen, and its stored rectangle is what returning restores.

## Understand the implementation

**Runtime invariant:** No companion is published. The panel entry registers the `main` slot with the single engine store and declares the layers it renders; the entry's disposal proves removal, independently observable through the `board.*` slot declarations.

<details>
<summary>Implementation internals — click to expand</summary>

One registration surface: `apply` composes the board as slots. The `main` panel entry declares `board.canvas`, `board.dock`, `board.omnibar`, and `board.minimap` and renders them through `renderSlot`; the canvas occupant declares `board.windows`; the window layer declares the keyed `board.window` (one registration per window type — the instance travels in owner props, so one occupant serves every window of its type) and the keyed `board.window.body` (one registration per body kind) and hands each frame the body dispatcher; the same `apply` registers the `sidebar.panellist` icon. The keyed keys are the `WindowKind` and `WindowBodyKind` unions, so a registration for an unknown key is a compile error. Board state is one `dsh-client-store` engine store declared at the panel entry — pan, zoom, viewport box, window map, z-order, and the element-selection flag — with pure draft actions (`setPan`, `setZoom`, `zoomTowardPointer`, `setViewport`, `addWindow`, `openWindow`, `moveWindow`, `resizeWindow`, `setWindowBodyKind`, `focusWindow`, `centerOnWindow`, `setWindowFullscreen`, `exitFullscreen`, `closeWindow`, `hydrate`, `setSelectingElement`). Durable layout is the Host settings namespace `ui-board`: `board-settings.ts` owns the versioned schema, `client/board-layout.ts` captures the store into the wire document and repairs a stored one, and `client/board-persistence.ts` adopts the first-frame cache and, through the shared settings describe mirror, the server document, and writes changes back debounced under the revision CAS. The window z-index band is capped below the floating chrome, and raising a window writes only that window's value, so the other windows keep their state identity. Every layer and frame reads that same handle through the framework `useStore` seat; components hold no subscriptions of their own — the header drag and each resize handle are leaves that read the zoom where their gesture starts, so a canvas zoom never re-renders a window body, and the chats panel subscribes to the view transform only while it is open. Visible copy is locale-owned: `apply` registers the `board` namespace dictionaries through `ctx.locale` and each copy-bearing entry declares the namespace, which puts the typed `t` seat on its component. Styling reads the shared theme directly: each component owns a CSS Module beside it, inline styles carry only placement and the computed pan/zoom metrics, and the rules name `--dsw-*` semantic aliases — floating panels use the theme's layer-2 fill with an elevation hairline (rebound to the business accent on the focused window), internal separators are 0.5px hairlines, and the canvas dot grid rides the border scale. Interactive chrome comes from `ui-primitives`: header close buttons and the composer actions are Harness icons, the dock rows and the composer action are wrapped in `Tooltip`, the Omnibox action menu is the shared `Menu`, and the dock controls sit on the floating-fill token. The board therefore follows the shell's light/dark preference like any other panel. Gestures have one owner: every drag (canvas pan, header, window resize, panel resize, row reorder) goes through `pointer-gesture.ts`, which ends on pointerup, pointercancel, or the owning component's unmount, so no listener or capture survives a gesture. The board root owns one non-passive wheel listener that skips a window lane or an open chats panel and zooms elsewhere, a `ResizeObserver` on the canvas container is the single owner of the measured viewport, and windows that leave the canvas hide with `content-visibility` — never unmounted — through `culling.ts`. Window sessions live in an apply-side bridge (`session-bridge.ts`): the window id → session map, the `sessions.create()`/`open()`/`binding()` sequence, and the chat/session subscriptions all stay in the plugin closure, never in the store, and each window's lane state — the assembled chat, the chat title, the history flags, the running calls, the image limits, and the turn and prompt failures — is republished through one identity-stable channel per window; closing a window drops its bridge record, while the session itself stays alive and listed. The map is durable: the bridge hands it to the persistence layer on discrete events (creation, rebind, close) and the settings section carries it as `bindings`, written as a complete-section replace so a closed window's pair actually leaves the section, and every adoption restores each window's chat; `sessions.list` is the authority that moves a bound window between restoring, ready, and missing, reattaching a chat that returns, and one session belongs to one window — `bind` reports duplicate, same, and unknown outcomes, and the panel and the Omnibox's recent-chat list bring the holding window forward instead of opening a second one. The frame and body registrations expose that channel as the keyed hook `useWindowSession(windowId)` plus the composer callbacks (`ensureWindowSession`, `sendPrompt`, `cancelPrompt`, `loadOlderTurns`, `executeCommand`, `uploadFile`), so one registration serves every window and components receive plain data; `uploadFile` stages non-image files through the host's background upload service and hands the composer a receipt the prompt or command carries. Board chrome shares its addressing and placement rules: `open-window.ts` resolves the chat window a command acts on (`resolveChatWindow` — the active chat window, else a fresh agent window), the store's `composerIntents` queue carries append-text and open-file-picker commands until `ComposerBar` consumes them (a file picker waits until the composer can accept files, and a closed window drops its queued commands), `element-capture.ts` builds the deterministic selector and language-neutral description behind the inspector chip, and `menu-placement.ts` is the single rule every board popover uses to open on the roomier side. The Omnibox's send goes through the bridge's `whenReady` wait, which settles once the window has a session — or its creation failed — so a prompt submitted as a window opens is not lost.

</details>

<a id="model-experience"></a>
## Model Experience

None, as the board is a browser-only canvas: it registers no tool, prompt section, or session event, and everything it renders is board-local view state.

#### KV Cache effect

No effect; the board adds nothing to any model request and consumes no session-log content.

## Known Limitations and Deferred Work

These limits are current package constraints.

- **The window lane renders prose, steering, tool cards, and turn failures** — assistant text arrives as Markdown and streaming text is visible; each tool call renders as its card (`bash`/`pwsh`/`terminal_send` as a terminal, `read` as a file window, `write`/`edit`/`str_replace_editor` as a diff, `grep`/`glob` as search results, `web_search`/`web_fetch` as citations, `todo_write` as a to-do list, `read_image` as an image preview, `ask_user_question` as an answered transcript), and a call the table cannot read — an unknown tool, a malformed result, a call head outside the loaded window — falls back to a collapsed JSON block. A running card shows its elapsed seconds and settles into the succeeded, failed, or stopped state, with the provider's own error text under a localized failure line. Transcript nodes outside that scope — compaction checkpoints, a turn that hit the output-token cap, and model retries — render nothing yet.
- **A pending approval or question banners the window and navigates to the main panel (decided for the MVP)** — the answering UI (allow or reject, the question flow) lives in the main panel's composer, so the window shows a localized `Confirmation required` (or `Answer required`) banner whose button selects the session and returns the main area to the Conversation; the window's own composer stays inert with the banner's title as its reason until the request is resolved. The board then brings the originating window forward with a short highlight when its panel comes back. No approval surface renders inline in the window.
- **The board's file chips are draft-only** — a non-image file stages through the host's upload service and ships as a receipt while its window lives; the chip keeps the name and the retry, not the bytes or the upload progress, and a receipt cannot be re-sent after its window closes. `@` mentions insert plain text rather than editor chips.
- **The window composer keeps its own submission policy (decided here)** — plain Enter queues, Cmd/Ctrl+Enter steers, and the bar reads no submission-preference setting: the `ui-conversation` `busyEnter` preference lives in that plugin's settings namespace and maps only the bare-Enter gesture, while the board's windows are documented to keep the queue/steer pair on the two gestures.
- **A command's failure line may be the host's own text** — a refused handler or a rejected attachment renders after “Command failed:” in the host's words, while an unmatched line shows the board's own unknown-command line; the failure stays until the next send. The board's palette adds its own `/file` and `/model` entries (file picker and model menu) to the host registry it lists.
- **A queue edit replaces text only** — the host's edit action accepts a non-empty text-only replacement, so a queued message whose other content blocks mattered loses them; the row's image thumbnails resolve through the session-scoped conversation cache and a failed read keeps the placeholder, and the turn-error card's repeat action queues a fresh turn because the client exposes no in-place turn retry.
- **A refused queue change stays on screen until the next queue action or send** — the strip renders the host's reason under its rows; there is no per-row error state.
- **Assistant markdown keeps the app's content font size** — the shared Markdown surface reads the app's font-size setting, so only the window's own chrome, transcript text, and composer take the window scale; raise the app's font size for larger assistant prose.
- **The chats panel has no unarchive and no session delete** — archiving a chat is one-way and the client exposes no delete for sessions, so the chat row menu's delete entry is inert; deleting a project removes its registration, never its chats or files.
- **The panel's folder browser reads the browse picker only** — a host that mounted the platform-native chooser serves no directory listing, so the level names that and hands the pick to the native chooser; there is no in-app browsing on such a host.
- **The dock and minimap stand down while a chats panel is open** — the panel is a management surface, and their strips would otherwise cover its outer edge and resize handle; collapsing the panel to its rail brings them back, and the frame's chats button reopens it.
- **An open chats panel stands the whole floating chrome down** — the expanded panel is a management surface, so the dock, the Omnibox, and the minimap stop rendering until it collapses to its rail; no root-level layer then covers the panel's outer edge, its resize handle, or the window's bottom edge in the overlay presentation.
- **Resize handles follow the active window above the chrome** — the handle ring is drawn for the focused window, so a window whose edge sits under the dock, omnibar, or minimap still needs one click anywhere on its frame before its handles rise above those layers.
- **The dock scrolls once the stack outgrows the panel** — one row per window does not fit a 900px panel past roughly a dozen windows, so the rail scrolls instead of clipping its rows and its add/reset controls.
- **Culling hides windows with a fixed world margin** — a window's contents stop painting and hit-testing once it is 480 world units beyond the visible canvas, whatever its size; its box keeps its place in the layout, the margin covers its handles and an open chats panel, and the window keeps its state while hidden.
- **Per-window setup comes from the composer** — the agent-preset chip switches the preset only while the session is still blank (the chip names that reason), the board remembers the last pick as the default for new windows, and the model chip switches the model and its reasoning effort; a model choice is also saved as the `agent-default-model` system default, which the chip's tooltip states. A preset never pins the model: the model is a session property, so two windows on one preset can run different models. A started session keeps its working directory, and only a still-blank session can be re-created in a newly picked folder.
- **The frame body dispatcher is an owner prop** — the windows layer is the single declarer of `board.window.body` (the slot core allows one declarer per key), so it passes each frame a `renderBody` callback instead of a `renderSlot` seat of its own.
- **The layout persists through the `ui-board` settings namespace, with MVP-scale limits** — windows, their geometry and order, pan/zoom, the active window, the chats-panel state, and the window → chat bindings live in the `ui-board` section of the user-settings document, so they survive a page reload and a process restart; a localStorage copy of the same document paints the first frame. Writes are debounced (600ms after the last gesture, at most one per second), so a crash inside that window loses the last gesture; with two tabs open, the losing writer re-reads the revision and the last writer wins. Fullscreen is session-only and the viewport box is measured, never restored. A document carries `version: 1`; an unrecognized version, or a layout the schema rejects, is ignored with a warning, and the MVP has no migrations — a future version starts from a fresh board. The bindings are reconciled against the layout on every adoption — a pair for a window the layout no longer holds is dropped — and a pair whose session is gone is kept so the window can report it and reattach if the chat returns. Closing a window removes its pair too: the board writes the whole section rather than a merge patch, because the settings service deep-merges a patch and a merge could never delete the key.
- **One window per chat, and a vanished chat is not replaced** — a chat another window already shows is never bound twice: picking it brings the holding window forward instead. A chat the host no longer lists leaves its window in the missing state with New session and Choose a chat; the MVP never auto-creates a replacement, and the client exposes no session delete, so those two actions are the only recovery the lane offers.
- **Tool and settings windows ship frames without content** — the dock's `+` catalog and the Omnibox's New window section open the agent, connectors, and settings windows, whose bodies stay empty, and clone, dashboard, and tasks windows have no creation path in the MVP; the real per-window fields arrive with the stages that own them, and a client system-prompt editor does not exist in Harness at all.
- **The dock status is a coarse four-state projection** — it reduces the window's session channel to Creating, Running, Idle, or Error with no per-tool progress; any creation, prompt, or turn failure shows Error.
- **The dock's rename and close live in the row's context menu** — no visible per-row close button exists; a right-click on the row opens the menu.
- **The inspector chip is plain draft text** — the composer has no editor chips, so the captured chip travels as text carrying a DOM description and a `:nth-of-type` selector, never a screenshot.
- **Workspace folders and project management live in the window chats panel** — working directory is immutable once a session is created (core engine constraint); new chats inherit the project's folder or run in the default working directory. The composer no longer carries a folder chip; all project creation, folder registration, path viewing, and quick actions ("Copy path", "Open folder in file manager") happen exclusively through the window chats panel.
- **Session artifacts are derived solely from settled tool results** — the board performs no filesystem scans and does not implement a file manager. Artifacts are gathered dynamically from successful file-access and mutation tool calls (`write`, `edit`, `str_replace_editor`, `read`) in the session's turn history, with path deduplication and mutation precedence (edits outrank passive reads). Each artifact row offers path copy and reveal in the system file manager via `session.openWorkspacePath`.
- **Isolation of user home and Ketos runtime state** — registering or setting workspace directories inside `~/.ketos` or `$DSH_HOME` is rejected both on host and client with localized validation errors; selecting a root directory (`/`, `C:\`) or the entire user home directory requires explicit confirmation.
- **The Omnibox's Web search and the clone, dashboard, and tasks windows answer with a localized unavailable-in-this-MVP notice** — their surfaces belong to the host or to later stages.
