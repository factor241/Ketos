# Agent Note: The clone interview is a per-agent scope derived from stored bindings and hosted by the clone window

Status: implemented

English | [中文](2026-09-21-ketos-stage-16-clone-interview.zh.md)

## Problem

Stage 15 gave a clone a stored record and an editor, but every authored field had to be typed by hand: nothing turned a conversation with the person into the record the later stages compose into an agent's prompt. The stage had to add a bootstrap interview — an agent that asks the checklist questions one at a time and finally writes the profile — without giving ordinary chats an interviewer prompt, without a second chat surface in the board, and without parsing a profile out of the model's prose. The interview must also survive a restart, must not re-open itself on resume, must stop being an interview the moment the profile is saved, and must leave the person able to review and correct what the agent wrote.

## Decision

**Interview mode is derived from two stored facts, not from a preset.** A session is interviewing while `clone_sessions` binds it to a clone with role `interview` and that clone's status is `interviewing`; `draft` is a record created by hand and `ready` is a saved profile awaiting review. The lifecycle narrowed from stage 15's speculative `draft | active | archived` to `draft | interviewing | ready`, because `active` and `archived` had no reader and the interview stage owns the transitions; schema step `v2` normalizes an existing file's `active` to `ready` and `archived` to `draft` without touching any other column, so no record is dropped and the runner stays forward-only. Deriving the mode from the binding and status rather than from a dedicated agent preset keeps a clone's ordinary working session an ordinary chat: only a session the board explicitly bound for an interview gets the interviewer instruction and the draft tool.

**One coordinator composes the mode into `agent.ctx`, and the shipped route tells it when stored data moved.** `src/interview.ts` reconciles on `agent/created`, `agent/session-start`, `agent/disposed`, and on a mutation notification the route now emits after an accepted write. The notification is what makes the shipped order work: `sessions.create()` creates the agent on the host, so the binding is written after the agent exists and no lifecycle event can observe it. Each reconciliation reads the two stored facts and drives one `agent.ctx.inject(['tools', 'systemPrompt'], …)` scope — register `clone_draft_save`, register the `clone:interview` section — so both contributions live and die with that agent and never enter the global registries: `ctx.tools.get('clone_draft_save')` is undefined for an ordinary session and the assembled prompt of an unbound agent contains no interview text. Reconciliations are chained per agent, so two overlapping triggers cannot install the scope twice; the in-flight install re-checks disposal after its await, so no scope outlives the plugin fiber.

**The profile arrives as validated tool arguments, and the save ends the mode.** `clone_draft_save` takes the role, the one-line description, the persona, the methodology, and the skill names; it resolves the bound clone from the calling agent's own session (`exec.agent`), writes the profile and marks the clone `ready` in one revision-checked update, and the tool result names the saved revision. The store enforces the mode where the write happens rather than trusting the scope's lifetime: a session without an `interview` binding is refused with `ketos/not-a-clone-session`, a clone that already left `interviewing` — for example a profile the person confirmed from the form first — with `ketos/clone-not-interviewing`, and a profile beyond the documented field bounds with `ketos/invalid-draft`, because a tool schema can express neither `maxLength` nor `maxItems`. All of them are `HarnessError`s, so the model reads the failure text and the durable `tool/result` carries `error.info.code`. The save reads the current revision in the same call, so the stored record always absorbs a user edit that landed earlier; the agent's write is last-writer-wins by design, because it *is* the draft, and the protection for a user's own text lives in the form. `skills` joined the update patch (stored as the existing `skills_json` column) because the profile carries the names the person listed.

**The interview opens with one durable kickoff turn.** On entering the mode the coordinator queues `agent.followup(createUserMessage(…))` with a package-declared source kind `ketos-clone-interview` and `form: 'notice'`, so the transcript renders the opening as a collapsed account instead of a typed user message while the stimulus stays ordinary durable input. What keeps it to one is the input that would carry it: the agent's own pending inbox is asked first, so a kickoff still waiting for its turn — including one a restart restored from the log — suppresses a second, and a host-only session projection folds "this session ever logged a kickoff source" as the durable answer. A kickoff a cancelled turn dropped is therefore queued again instead of leaving the session waiting silently, while a logged one is never reopened. Triggers are collected per microtask and each agent reconciles through its own chain, so the `agent/created` and `agent/session-start` pair a publication emits together derives the mode once — reconciling twice would queue the opening turn twice, because neither the inbox nor the projection has caught up with it yet.

**The clone window hosts the interview as its own second body, and the section text stays static for the cache.** The clone window keeps `cloneId` and gains the `conversation` body kind for the interview: a two-tab strip between the header and the body (`CloneWindowBar`) switches between the card form and the window's own Harness session, which is the ordinary conversation body and composer — no second chat surface. `resolveChatWindow` and `conversationWindow` treat a conversation-bodied clone window as a chat target, which supersedes stage 15's exclusion: that exclusion was about a window whose body could never show a session. Starting the interview is one apply-side operation in a defined order — mark the clone `interviewing` under the roster revision, create the session, bind it with the role `interview`, `bridge.adopt` it into this very window, apply the clone's preferred model route, switch the body to the conversation — so the host sees status and binding together when it composes the agent. The prompt section is a static checklist text with a package-local order (`700`; `getSectionOrder` owns the repository-wide slots), so the request prefix an interviewing session assembles stays byte-identical between turns, and withdrawing the mode at `ready` is the one intended prefix change. The strip derives the clone's status from the roster and re-reads that roster whenever a turn settles, which is how a profile the agent saved reaches the form; the form marks the stored fields that moved, keeps a dirty draft's text, and exposes the stored revision as a pending row the user applies with one click, so the agent can never silently overwrite what the person typed. That draft and those marks live in the board store keyed by clone, not in the body component: the window unmounts the editor while the user answers in the interview body, and remounting must not drop either. The window is also named by the record it edits rather than by the chat inside it — the title ladder ranks the clone above the session's generated title — so the interview cannot rename the record's own window.

## Alternatives considered

- **A dedicated interview agent preset.** Rejected: the mode is per-session state (which clone, which status) that turns on and off during the session's life, while a preset composes a session's whole setup at creation; the stage also keeps preset selection a user-facing choice.
- **A global prompt section whose `text()` provider returns `''` outside the mode.** Rejected: the contribution would exist in every agent's assembly, the mode's ownership would live in a string function rather than in a scope, and the plan's removal-at-`ready` requirement is exactly scope disposal.
- **Installing the mode only at `apply` over `ctx.agents.roots()`.** Rejected: the shipped browser order creates the session before it binds it, so no lifecycle event observes the binding; without the route's mutation notification the mode would never turn on for a fresh interview.
- **Reading the profile out of the agent's final message.** Rejected: this repository does not parse model prose for structured results, and a tool schema validates the fields before anything reaches the store.
- **Storing the kickoff flag in `clone_sessions`.** Rejected: the session log is the durable authority for "was this session opened"; a column would make a crash between queueing and claiming either double-open the session or leave it silently unopened.
- **Keeping `active` and `archived` in the lifecycle.** Rejected: no consumer ever read them, and a four-state lifecycle whose two extra states mean nothing invites the UI to offer transitions the product does not have.
- **A separate clone-interview window, or a panel inside the clone window.** Rejected: the plan pins the interview to the clone window, and the window already owns the frame, chats panel, layout entry, and fullscreen behavior; a second window would also fight the one-session-one-window rule.
- **Tracking topic-level interview progress.** Deferred: the honest MVP report is the `interviewing` status plus the exchange count the transcript already provides; a checklist counter would need the agent to report topics reliably before it means anything.

## Consequences

The first product scenario of the fork now runs end-to-end: a person starts an interview from the clone window, answers the agent's questions in the same window, and reviews the profile the agent saved, with the clone's status moving `draft` → `interviewing` → `ready`. Later stages compose the `ready` profile into working sessions, and the memory stage inherits both the binding table and the per-agent scope pattern. The costs accepted: the mode is re-derived (a database read per lifecycle event and mutation) rather than cached, so entering or leaving it takes a turn of the event loop rather than being synchronous; the agent's save is last-writer-wins against the store, with the form — not the tool — protecting a user's unpublished text; a user's mid-interview card edit that already saved is absorbed into the draft the agent writes; the interview has no topic-level progress; and `skills` still round-trips with no consumer until the methodology stage.
