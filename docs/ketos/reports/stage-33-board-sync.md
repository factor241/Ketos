# Этап 33. Синхронизация общей доски

## 1. Итог этапа

Подготовка worktree (`pnpm install`, `pnpm run build`, `pnpm run typecheck`, `pnpm exec vitest run packages/client/ui-board/tests`) — зелёная до начала правок (852 теста). Этап выполнен в отдельном worktree `stage-33` рядом с основной папкой репозитория, ветка `stage-33-board-sync` от принятой `stage-32-iroh-peer`; коммита нет — по правилам линии он делается после ответа «да». Две доски стали одной общей: `@ketos/board-doc` отдаёт векторы состояния и принимает чужие обновления, `@ketos/peer` обменивается ими двоичными рамками 3–4 на каждом подключении, окна публикуются отдельными записями (`windows`, `window.put`/`window.remove`) и видны второй Кетос заглушкой с подложкой владельца, чужие элементы и окна только читаются, данные отключённого собеседника помечаются «Нет связи», а правки без связи догоняются после подключения. Доработки по ходу: `doc.patch` теперь пишет только изменённые поля (иначе одновременная правка `x` на A и `text` на B теряла одно из изменений — эксперимент плана); в `packages/client/tsdown.client.ts` `@ketos/board-doc/windows` добавлен в брандмауэр браузерно-безопасных подпутей; штриховые границы новых значков приведены к 0.5px и `corner-shape: round`; каталог слотов и каталог Config пересобраны; корпус ru-ключей дополнен четырьмя ключами. Ничего не пушилось и не коммитилось; `~/.ketos` не трогался (проверки — на стенде Docker). После комплексной проверки этапов 27–33 этап доработан в том же worktree (§6): исправлены блокер Б1 (`.env` в образе) и найденные недостатки протокола, публикации окон, хоста, стенда и клиента, добавлен гейт `verify-client-css-tokens`, измерения сняты на топологии «только ретранслятор», записан новый GIF.

## 4. Отклонения

Первые две строки и строка про `duplication` описывают состояние до доработки; итог доработки — §6 (что не сделано — §6.5).

- **Буквальная проверка «на двух компьютерах в разных сетях» не выполнена: второй физической машины нет.** Все живые проверки этого этапа — на двух контейнерах стенда на одной машине, где оба Кетоса делят часы хоста (смещение между ними ≈ 0), а путь — прямое соединение по сети Docker. Ретрансляторный путь измерен на этапе 32 (проба «только ретранслятор» — 0.229 с); сети покажет этап 36. Погрешность часов в отчёте: `sntp time.apple.com` до замера `+0.182 с`, после `+0.306 с` (Mac против Apple NTP; на измерение не влияет, так как отправитель и получатель идут по одним часам, а на двух машинах смещение передаётся `sync-latency.mjs --offset-ms` (на сколько часы отправителя впереди часов получателя) и прибавляется к результату).
- **`DSH_SNAPSHOT=replay pnpm run test:web` красный только на `plugin-install-github.e2e.ts` (2 теста).** Та же пара падает и на принятой базе `stage-32-iroh-peer` (проверено тем же прогоном), то есть это средовое ограничение песочницы, а не регрессия этапа; остальные 166 файлов и 647 тестов зелёные.
- **`pnpm run duplication` красный на том же наборе клонов, что и база.** На `stage-32-iroh-peer` — те же 5 клонов (`WindowFrame.tsx`, `tool-card-labels.ts` ×2, `pack-ru.ts`, `board-todo/wire.ts` ↔ `clone-core/wire.ts`); задача `ketos-7bs` описывает 4 из них, пятый присутствует и на базе. Этап новых клонов не добавил. Отдельного устранения не делалось (вне показа).
- **Переданное окно проверено юнит-тестом, а не живым прогоном.** Живой сценарий передачи требовал бы передачи окна между участниками через интерфейс на двух браузерах; поведение «чужое даже при `ownerId` = получатель» зафиксировано в `foreign-windows.client.spec.tsx` и в Known Limitations.
- **Публикация окон не отражает изменение `z`.** Подъём окна не публикуется (по плану), поэтому порядок чужих заглушек у получателя обновляется при следующей реальной публикации; запись всё равно несёт `z` на момент публикации.
