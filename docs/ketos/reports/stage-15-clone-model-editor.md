# Этап 15. Клон сотрудника: модель данных и редактор

## 1. Итог этапа

Появился первый хост-пакет Кетоса `@ketos/clone-core`: клон — запись с ролью, персонажем, методологией, предпочтительной моделью и привязками сессий, хранимая в `~/.ketos/clones.db` (SQLite, WAL, `application_id` + `user_version`, каталог `0700`/файл `0600`). Браузер работает с ней через точный Fetch-маршрут `/api/ketos.clones` без кодогенерации, а окно-редактор живёт в существующем `ui-board` новым телом `clone`; клон создаётся, редактируется (CAS по `revision`), переживает перезапуск, и его сессия привязывается в `clone_sessions`. Ветка `stage-15-clone-model-editor`, worktree `/Volumes/Projects/Ketos bot.worktrees/stage-15` от `stage-14-multi-window-perf`.

## 4. Отклонения

- **Формат предпочтительной модели — `provider/model`.** План оставляет формат открытым; строка из двух частей не требует каталога при применении и совпадает с представлением маршрута в `core/agent/model-selection.ts`. `parseModelRoute` делит по первому `/`, поэтому модель со слэшем в id сохраняется.
- **Удаление клона удаляет и его привязки.** План этого не оговаривает; брошенная привязка не разрешается ничем, поэтому `deleteClone` сносит `clone_sessions` в одной транзакции, а сами сессии остаются обычными сессиями.
- **Рабочая директория сессии клона не задаётся.** План пишет `ctx.sessions.create({ cwd })`, но у записи клона нет поля каталога: сессия создаётся как обычный новый чат доски (каталог выбирается в панели «Чаты»), и это поведение совпадает с новым окном агента.
- **Неожиданный отказ маршрута — 500 без кода.** Три кода плана описывают доменные ошибки; внутренний сбой (например, недоступная БД) отдаёт `500` с текстом, чтобы клиент не принял его за конфликт. Записано в README пакета.
- **Путь маршрута в клиенте — литерал.** Клиент импортирует из пакета только типы (`./types`), поэтому `clone-api.ts` держит `/api/ketos.clones` рядом с видами ответов; это зафиксировано в README пакета.
- **Побочный эффект предпочтительной модели.** Применение модели на сессии клона идёт штатным `remote.session.selectModel`, который также сохраняет выбор как `agent-default-model`; это разрешено планом на этом этапе и уже описано в Known Limitations `ui-board`. Применение модели — best-effort: отказ попадает в канал чат-окна, а не в редактор.
- **Покрытие.** Новые исходники попадают в именованные исключения MVP-политики (`packages/client/ui-board/src/**`, `packages/ketos/clone-*/src/**`), поэтому сигнал дают поведенческие тесты, а не проценты; команда из таблицы проверок (`--coverage.include='packages/client/ui-board/src/**'`) отвечает пустой сводкой именно из-за исключения.
- **Ожидание превью-смоука расширено.** `apps/web/tests/preview-boot.e2e.ts` теперь перечисляет `/api/ketos.clones` среди ожидаемых 404 статического превью: в этом скаффолде хост-пакет клонов не смонтирован, и ростер клонов законно пуст.

## 4a. Перепроверка (независимый аудит)

Этап перепроверен тремя независимыми аудитами (хост-пакет, клиентский слой, интеграция/документация/гейты); каждый нашёл подтверждённые дефекты, они закрыты в том же этапе отдельным коммитом `fix(ketos): close the stage-15 re-verification findings`. Исправленное:

| Находка | Что было не так | Исправление |
|---|---|---|
| Миграция не была атомарной | Крэш между DDL и версионным штампом оставлял файл с таблицами и `user_version = 0`; повторное открытие падало на `CREATE TABLE` и файл становился нерабочим | Шаги и штамп `user_version` коммитятся одной транзакцией (`schema.ts`), упавший шаг откатывается; тест на откат |
| Отказ открытия кэшировался | Транзиентный сбой (блокировка, права) отклонял каждый последующий запрос до перезапуска процесса | Неудачная попытка не кэшируется; тест «после устранения препятствия открытие проходит» |
| Гонка закрытия и первого открытия | Вызывающий мог получить репозиторий поверх уже закрытого хендла | Открытие отклоняется, если диспоуз выиграл гонку; тест обновлён |
| CAS удаления вне транзакции | Проверка ревизии и `DELETE` были разными statement'ами — другой процесс мог успеть записать между ними | Guard ревизии входит в сам `DELETE ... AND revision = ?` внутри `BEGIN IMMEDIATE` |
| Валидация после открытия БД | Мусорный `POST` на недоступной БД отвечал `500` вместо `400` и создавал файл на здоровой | Все поля разбираются до `database.repository()`; тест «400 не создаёт файл» |
| Черновик терялся при конфликте | Обновление ревизии пере-засевало форму, баннер обещал «сохраните снова», а сохранять было уже нечего | Ревизия перебазируется без замены черновика, повторное сохранение применяет правки; тесты на конфликт и повтор |
| Окно клона принимало чат-жесты | Omnibox/панель/инспектор адресовали промпты окну-редактору и создавали невидимую сессию («клон — не сессия») | `resolveChatWindow` больше не считает `clone` чат-окном, а связывающие сессию действия панели открывают чат-окно; тесты |
| Сессия могла остаться непривязанной | При отказе `bindSession` чат-окно уже было открыто с сессией, не привязанной к клону | Привязка выполняется до открытия окна; отказ докладывается редактору |
| Удаление при исчезнувшем клоне не согласовывало ростер | Форма оставалась на устаревшей записи; конфликт удаления показывал текст про сохранение | Ростер перечитывается, для удаления отдельный текст `clone.delete.conflict` |
| Ошибка чтения ростера выглядела как «клон удалён» | Первый неудачный запрос публиковался как `loaded` | `loaded` только после успешного чтения, в редакторе — состояние загрузки с кнопкой «Повторить» |
| Док не показывал имя клона | Строка дока падала на «Agent #N», тогда как заголовок окна показывал имя | Строка дока читает `cloneList` и передаёт имя в `windowTitle`; тест |
| Тихая ошибка «Новый клон» и гонка чтений | Отказ создания не показывался; устаревший ответ ростера мог затереть только что созданную запись | Уведомление об отказе в Omnibox; счётчик поколений чтений |
| Форма не знала границ маршрута | Слишком длинные значения отклонялись хостом с «повторите» — повторить было нельзя | `maxLength` полей равен границам маршрута; тест на атрибуты |
| Устаревшие утверждения в документах | README не описывал `500`; путеводитель `ui-board` говорил о сессии у окна клона; политика MVP и комментарий `vitest.config.ts` — «пакеты клонов не существуют»; нота слотов называла снятый `ToolWindow`; каталог слотов был сгенерирован до последней правки `slots.ts` и `verify-client-catalog` падал | Все тексты приведены к коду (en+zh), каталог перегенерирован, `doc-sync` перепроверен |
