# Agent Note: Board layout persistence through the ui-board settings namespace

Status: implemented

English | [中文](2026-09-18-ketos-board-layout-persistence.zh.md)

## Problem

Stages 4–7 built the board's window model, sessions, chats panel, fullscreen mode, gestures, and culling, but every restart threw the arrangement away: `apply` created the store without a persist key, the `createBoardStore` option existed unused, and the host half of `@deepseek-ai/dsh-client-ui-board` was an empty `apply()`. The stage requires that a reload or a process restart restore the windows and the viewport. The layout is a user-settings document rather than session data, and the settings domain already provides schema validation, a monotonic namespace revision, and compare-and-set writes over the client Remote face, so the stage adds no wire namespace and no Typert code generation. The constraints: the settings file is one YAML document with locking and atomic replacement, so writes must be rare and discrete; the browser cannot block its first render on the settings round trip; a hand-edited or older document must never break the board; and two open tabs may race.

## Decision

**The durable layout is the `ui-board` settings namespace.** `src/board-settings.ts` owns the namespace name, `version: 1`, the restore limits, and the schemastery schema; the host half registers it through `ctx.inject(['settings'], (settingsCtx) => settingsCtx.settings.register(...))`, exactly like `ui-theme`. The schema defaults every field, so the namespace resolves without a user section. The document carries `panX`, `panY`, `zoom`, `windows[]` (`id`, `kind`, `bodyKind`, `ordinal`, optional `customTitle`, `x`, `y`, `width`, `height`, `zIndex`), `windowOrder`, `activeWindowId`, and the chats-panel state (`panelWindowId`, `panelCollapsed`, `panelWidth`, `panelGroupBy`, `panelOrderBy`). `viewportWidth/Height` are absent because the canvas measures them, and `fullscreenWindowId` is absent because fullscreen is a session modality. Nullable identities travel as `''`, because schemastery cannot materialize a `null` default through an object schema; `''` is no window.

**One store instance backs the renderer and the persistence layer.** `apply` builds the handle, creates one instance, and passes `{ ...handle, create: () => instance }` to every `register` call, while the persistence layer works on the instance directly. The renderer's store seat keys instances by handle and would otherwise mint its own instance from the same handle, so the wrapper is what makes `instance.actions.hydrate()` visible to the components.

**The first frame comes from a localStorage copy; the server document is the source of truth.** `client/board-persistence.ts` caches `{ revision, layout }` under `dsh.board.layout` after every accepted write and adopts it synchronously before registration, so a reload paints the previous arrangement with no empty-canvas flash. The board then derives from the shared settings describe mirror (`ctx.settingsScope.describe()`), which is the client's one `settings.describe` reader: the mirror subscription and its held snapshot add no wire read of their own, so the startup RPC budget stays with `ui-settings`, and a non-loopback page whose mirror stays `unavailable` neither adopts nor writes. Once the mirror holds a ready view, the `ui-board` namespace is adopted when it carries a user section; without a first-frame cache the document is adopted whatever its revision (it is the only layout that browser has), and with a cache the server wins when it is ahead while a server revision behind the cache means a write was lost inside the debounce or during teardown, so the cached document is pushed back. An absent namespace or a sanitizer that refuses the document leaves the local layout in place, and the schema-default value of an unwritten namespace is never adopted, which is what keeps the cache alive across restarts.

**Writes are debounced, serialized, and revision-checked.** A store subscription schedules one write 600ms after the last change and never sooner than one second after the previous write. The stage split frequent pan/zoom from discrete window changes; the shipped scheduler keeps one debounce for both, because the pause is already the final snapshot for the frequent class and the floor covers the discrete class, so the observable contract — one write after a gesture pauses, never more than one per second — holds without two timers. The flush captures the document, skips it when it equals the last accepted one, and calls `ctx.remote.settings.update('ui-board', doc, revision)` with the revision the mirror holds at that moment. The answer is folded back through `acceptView`, which updates the held revision; `settings/conflict` triggers exactly one retry at the `actual` revision the conflict reports (that number is the re-read the plan asks for, without a second wire round trip), last writer wins. A refused or failed write keeps the layout in the store and the next change retries; no failure path reaches the components.

**Every read is repaired, not rejected.** `client/board-layout.ts` captures the store into the document and `sanitizeBoardLayout()` adopts a stored value leniently: a window without an id, of an unknown `kind`/`bodyKind`, or a duplicate identity is dropped, negative sizes are repaired to their magnitude and then to the minimum window, coordinates, zoom, and panel width are clamped, the paint order is renormalized from `windowOrder`, a dangling `activeWindowId`/`panelWindowId` becomes none, a panel without an owner window reads as closed, and an overfull document keeps its 50 topmost windows. `captureBoardLayout` applies the same topmost-50 slice and drops ids with no window, so a board past the restore cap still persists and the schema never refuses an overfull write. The repaired candidate must still satisfy the settings schema before the board adopts it, and a document whose `version` is not 1 is ignored with a warning: the MVP has no migrations, and a future version starts from a fresh board.

**Only the layout fields move on hydration.** The `hydrate` action writes the stored fields and clears `fullscreenWindowId`; the measured viewport and transient interaction state (selection mode, queued composer intents) stay with the running session. The localStorage copy stores the same document, never the store state, so no transient field can outlive a reload.

Wiring: the client `inject` list adds `settingsScope` and `remote.settings`; `@deepseek-ai/schemastery` moved into `dependencies` (the host half imports it), while `@deepseek-ai/dsh-settings`, `@deepseek-ai/dsh-client-ui-settings`, and `@deepseek-ai/dsh-api-remotes` are development-only type sources, which is what `verify-package-dependencies` requires. The panel width bounds and the chats-panel grouping and ordering enums moved into `board-settings.ts` so the schema owns every restored value and no top-level client module imports a domain directory.

## Alternatives considered

- **The `defineStore` `persist` option as the cache (implemented first, removed).** It persists the whole `BoardState`, including selection mode, queued composer intents, the viewport box, and the session-only fullscreen id — resurrecting an inspector chip or a fullscreen frame after a reload — and it carries no revision to compare against the server. The explicit document cache stores exactly the wire document plus the revision it was written under.
- **A private `ctx.remote.settings.describe()` read (implemented first, removed).** It duplicated the client's one describe reader, added a third `settings.describe` to the startup RPC budget, and bypassed the loopback persistence policy: a remote browser would have read and written the operator's `ui-board` YAML section. Deriving from `ctx.settingsScope.describe()` reuses the shared read, its invalidation refresh, and its write-answer fold.
- **A bound `settingsScope.bind({ namespace: 'ui-board' })` scope instead of the describe face.** The scope's snapshot would have supplied the decoded value and revision with no extra read, but its write path (`set`/`unset`/`mutate`) recovers from a conflict by reloading Host state rather than re-applying the tab's document, and the stage fixes last-writer-wins with one retry as the MVP policy. The describe face plus the direct `remote.settings.update` keeps that policy explicit while still sharing the read and the fold.
- **A `@ketos/board` package with `board.db`.** Deferred to post-MVP by the master plan: the layout is a small user-settings document, and the settings seam already supplies validation, revision, and CAS without a new package, wire route, or SQLite lifecycle.
- **Write on every pan and zoom frame.** Rejected: the settings file is locked and atomically replaced per write, and the budget is at most one write per second; the debounce plus the minimum interval also makes a gesture commit after its pause rather than during it.
- **Reject a stored document the schema dislikes.** Rejected: the client-side value can come from a hand-edited document, an older version, or a partial write, and one broken window must not cost the whole layout. Repair plus a final schema check keeps the invariant while preserving the healthy windows.
- **`settings.mutate` with path-addressed ops.** Rejected for the MVP: the document is small, `update` merges the complete patch over the section, and one path per window would add bookkeeping without a size benefit.
- **Merge the re-read document on a conflict.** Rejected: two tabs have no meaningful merge for a spatial layout, the plan fixes last-writer-wins as the MVP policy, and the re-read is what makes the retry land instead of conflicting forever.
- **Store the sessions in the layout document.** Rejected: session identity belongs to the bridge (stage 9 restores bindings), the settings document must stay JSON-compatible and small, and the window state must remain identical for every window that never had a session.

## Consequences

A reload and a process restart now restore the windows, their geometry, the paint order, the active window, pan/zoom, and the chats-panel state, while a fresh deployment still starts empty. The costs: a crash inside the 600ms debounce loses the last gesture; two tabs resolve to the last writer at the revision the conflict reported; the localStorage cache can show a stale layout for one frame when another tab wrote in between (the startup adoption replaces it); the restore caps a document at 50 windows and clamps coordinates, zoom, and panel width, dropping beyond-limit windows rather than refusing the document; and there are no migrations between layout versions, so a future `version: 2` starts from a fresh board until a migration exists. The board is also now a settings namespace owner on the host: without a settings provider the registration waits, and the client still hydrates from its cache but writes nowhere. The board adds no settings wire read of its own, so it inherits the client's startup read budget and loopback persistence policy instead of duplicating them.

Verification: `tests/board-settings.client.spec.ts` (schema acceptance, defaults, every rejection class), `tests/board-host.client.spec.ts` (host registration, write validation, disposal, and absence without a provider), `tests/board-layout.client.spec.ts` (capture round-trip with 20 windows, unknown version, missing id, duplicates, negative sizes, clamped ranges, z-order renormalization, the 50-window cap, the panel rule), and `tests/board-persistence.client.spec.ts` (cache adoption, corrupt cache, server-ahead adoption with revision reuse, equal-revision adoption without a cache, adoption when the mirror answers after start, server-behind push-back, sanitizer refusal, unavailable-mirror silence, read-only provider, debounce coalescing, the one-per-second floor, the captured 50-window cap, conflict retry at the reported revision, refused and throwing transports, dispose, shared-instance hydration through the panel store, and a mount with no describe method on the remote double).
